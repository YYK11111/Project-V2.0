# 项目健康度指标说明

## 1. 文档目的

本文档用于明确项目健康度的定义方式、指标组成、评分建议和使用边界，为后续项目驾驶舱、项目报表、预警机制和管理分析提供统一口径。

本文档主要解决以下问题：

1. 项目健康度到底是什么
2. 应该由哪些维度组成
3. 每个维度的数据从哪里来
4. 当前阶段适合做到什么程度
5. 后续如何逐步演进为更成熟的经营指标体系

---

## 2. 核心定义

项目健康度不是单一字段，也不是单一页面上的一个颜色标签，而是对项目当前整体运行状态的综合判断结果。

建议定义为：

**项目健康度 = 对项目在进度、风险、变更、执行透明度、交付达成和知识沉淀等方面的综合评估结果。**

健康度的目标不是替代项目经理判断，而是：

1. 帮助管理层快速识别异常项目
2. 帮助项目经理更早发现偏差和风险
3. 帮助驾驶舱、报表和预警形成统一口径

---

## 3. 项目健康度的使用场景

项目健康度建议用于以下场景：

1. 项目驾驶舱总览
2. 项目列表排序与筛选
3. 项目详情页状态提示
4. 经营分析报表
5. 管理层周报、月报摘要
6. 异常项目预警识别

项目健康度不建议直接用于：

1. 替代审批结论
2. 直接做绩效考核依据
3. 在数据口径尚未稳定时做严格排名

---

## 4. 健康度总体结构

建议将项目健康度拆成六个一级维度：

1. 进度健康度
2. 风险健康度
3. 变更健康度
4. 执行透明度
5. 交付达成度
6. 知识沉淀度

这六个维度既覆盖项目执行，又覆盖项目治理，还能与现有系统能力较好对齐。

---

## 5. 一级指标说明

### 5.1 进度健康度

反映项目在时间计划上的稳定程度。

建议参考指标：

1. 项目是否接近结束日期仍存在大量未完成任务
2. 里程碑延期数量
3. 逾期任务数量占比
4. 计划与实际偏差情况

当前阶段可先以以下信号作为简化判断：

1. 逾期任务数量
2. 即将到期里程碑数量
3. 项目整体进度与结束时间的匹配情况

### 5.2 风险健康度

反映项目风险暴露程度及风险管控效果。

建议参考指标：

1. 高风险数量
2. 已逾期未关闭风险数量
3. 风险关闭率
4. 风险升级数量

当前阶段可先以以下信号作为简化判断：

1. 高风险数量
2. 风险总数
3. 严重风险是否存在长期未处理情况

### 5.3 变更健康度

反映项目变更对项目稳定性的影响。

建议参考指标：

1. 待审批变更数量
2. 高影响变更数量
3. 变更频率
4. 变更对进度和成本的影响度

当前阶段可先以以下信号作为简化判断：

1. 待审批变更数量
2. 高影响变更数量
3. 近期变更数量

### 5.4 执行透明度

反映项目执行过程是否可见、可跟踪、可管理。

建议参考指标：

1. 任务汇报覆盖率
2. 最近 7 天未汇报任务数量
3. 评论活跃度
4. 工时记录完整度

当前阶段可先以以下信号作为简化判断：

1. 最近 7 天未汇报任务数
2. 无评论任务数
3. 工时记录覆盖情况

### 5.5 交付达成度

反映项目交付成果和关键承诺节点的完成情况。

建议参考指标：

1. 里程碑达成率
2. 已完成任务占比
3. 关键任务按时完成率
4. 结项前关键事项是否闭环

当前阶段可先以以下信号作为简化判断：

1. 已完成任务占比
2. 已完成里程碑数量占比
3. 项目整体进度

### 5.6 知识沉淀度

反映项目过程中是否形成了可复用、可管理的知识资产。

建议参考指标：

1. 项目知识数量
2. 最近更新知识数量
3. FAQ 或复盘类知识数量
4. 项目复盘是否沉淀完成

当前阶段可先以以下信号作为简化判断：

1. 项目知识总数
2. 最近更新知识数
3. 是否已有复盘类知识

---

## 6. 推荐评分模型

当前阶段建议采用“分维度打分 + 总分区间映射”的简化模型，避免一开始做过于复杂的统计算法。

建议总分为 100 分，六个维度分别给出权重。

推荐权重如下：

1. 进度健康度：25 分
2. 风险健康度：20 分
3. 变更健康度：15 分
4. 执行透明度：15 分
5. 交付达成度：15 分
6. 知识沉淀度：10 分

推荐映射规则：

1. 85-100：健康
2. 70-84：基本健康
3. 50-69：需关注
4. 0-49：高风险

当前阶段的重点不是分数绝对精确，而是确保：

1. 评分逻辑稳定
2. 指标来源清晰
3. 趋势变化可解释

---

## 7. 当前阶段建议的简化口径

为控制实施复杂度，V1.3 阶段建议先采用“简化健康度口径”，只基于当前已有数据能力构建。

建议第一版健康度主要使用以下数据：

1. 项目整体进度
2. 逾期任务数
3. 高风险数
4. 待审批变更数
5. 最近 7 天未汇报任务数
6. 里程碑完成情况
7. 项目知识数量或最近更新知识数量

这样可以在不大幅改造底层模型的前提下，先形成一版可用的健康度视图。

---

## 8. 数据来源建议

### 8.1 项目层

来源字段或聚合：

1. `project.progress`
2. `project.startDate`
3. `project.endDate`
4. 项目状态与审批状态

### 8.2 任务层

来源字段或聚合：

1. 逾期任务数量
2. 已完成任务数量
3. 最近汇报时间
4. 评论数量
5. 工时记录情况

### 8.3 风险层

来源字段或聚合：

1. 高风险数量
2. 风险总数
3. 未关闭风险数量

### 8.4 变更层

来源字段或聚合：

1. 待审批变更数
2. 高影响变更数
3. 近期变更数

### 8.5 里程碑层

来源字段或聚合：

1. 里程碑总数
2. 已完成里程碑数
3. 即将到期里程碑数
4. 延期里程碑数

### 8.6 知识层

来源字段或聚合：

1. 项目知识总数
2. 最近更新知识数
3. FAQ 或复盘类知识数

## 9. 展示建议

### 9.1 驾驶舱展示

建议在项目驾驶舱中展示：

1. 项目健康度总分
2. 健康等级标签
3. 六个维度的子分数
4. 重点扣分原因

### 9.2 项目详情页展示

建议在项目详情页展示：

1. 健康度标签
2. 重点异常提示
3. 主要风险来源

### 9.3 报表展示

建议后续在报表中展示：

1. 各项目健康度分布
2. 健康度趋势变化
3. 高风险项目排行

---

## 10. 使用边界与注意事项

### 10.1 健康度不是绝对真相

健康度本质上是一个“管理辅助判断模型”，不能替代项目经理的业务判断。

### 10.2 健康度需要明确口径

一旦在驾驶舱或报表中展示，就必须固定数据口径，否则不同页面的分数会失去可信度。

### 10.3 第一版不追求过度精细

V1.3 阶段建议先做“稳定、可解释、可追踪”的健康度，而不是一开始做非常复杂的评分模型。

### 10.4 指标迭代应慎重

一旦健康度进入管理视图，评分逻辑频繁调整会影响用户信任，因此后续权重和指标调整应纳入版本管理。

---

## 11. 分阶段建设建议

### 11.1 第一阶段：建立简化健康度

目标：让项目健康度先出现在项目视图中。

建议内容：

1. 形成六维简化模型
2. 用现有项目、任务、风险、变更、里程碑和知识数据打分
3. 在项目驾驶舱中展示总分和等级

### 11.2 第二阶段：增强指标质量

目标：让健康度从粗判断升级为更稳定的管理指标。

建议内容：

1. 引入计划偏差数据
2. 引入里程碑延期和达成率
3. 引入工时和汇报质量指标
4. 优化各维度评分逻辑

### 11.3 第三阶段：健康度进入经营分析

目标：让健康度成为管理报表和经营分析的稳定指标。

建议内容：

1. 做趋势变化分析
2. 做项目对比分析
3. 做异常原因拆解
4. 与预警和治理动作联动

---

## 12. 最终结论

项目健康度应被视为项目治理和经营分析中的核心指标之一，但当前阶段必须采用“可解释、可稳定、可逐步演进”的建设策略。

建议顺序为：

1. 先建立简化健康度模型
2. 再补计划偏差和交付达成指标
3. 最后进入完整的经营分析与预警体系

只要指标定义清晰、数据口径统一、评分规则稳定，项目健康度就能成为项目管理专项中最有价值的管理指标之一。
