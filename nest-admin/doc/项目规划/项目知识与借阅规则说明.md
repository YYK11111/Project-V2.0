# 项目知识与借阅规则说明

## 1. 文档目的

本文档用于明确项目知识的组织方式、角色边界、访问规则、借阅规则和后续演进方向，确保项目知识整合落地时，产品、研发和业务侧对规则理解一致。

本文档主要回答：

1. 什么是项目知识
2. 项目知识如何组织
3. 项目成员和非项目成员如何访问项目知识
4. 当前借阅规则怎么运行
5. 项目知识与知识中心、项目管理、借阅审批之间的关系是什么

---

## 2. 核心定义

项目知识是指在项目生命周期内产生、维护和沉淀的各类知识资产，包括但不限于：

1. 项目概况资料
2. 需求与方案说明
3. 实施交付文档
4. 运维支持 FAQ
5. 项目复盘与经验总结

项目知识不是独立于知识中心的新系统，而是知识中心在项目场景下的专项应用形态。

因此，项目知识的基本原则是：

1. 组织上依托知识中心分类体系
2. 权限上依托项目成员关系和知识责任人关系
3. 借阅上沿用知识中心现有借阅机制
4. 后续在项目上下文中增强搜索、复盘和智能能力

---

## 3. 项目知识的组织方式

### 3.1 组织原则

项目知识不再继续走“项目文档模块”独立演进路线，而是统一收口到知识中心，通过“项目知识分类”方式进入项目主线。

### 3.2 根分类

系统统一维护根分类：

- 项目知识

所有项目知识主分类都挂在此根分类下。

### 3.3 项目主分类

每个项目在立项审批通过后自动创建一个项目主分类。

命名建议：

- 项目编号-项目名称

例如：

- PRJ-20260418-001-某某实施项目

### 3.4 预制子分类

项目主分类下默认生成以下子分类：

1. 项目概况
2. 需求与方案
3. 实施交付
4. 运维支持
5. 项目复盘

### 3.5 为什么采用分类而不是文章直接挂项目

原因如下：

1. 当前知识中心已经是分类驱动模型
2. 分类天然适合承载权限和借阅策略
3. 分类更适合后续知识治理和归档
4. 改造成本更低，兼容现有结构更好

---

## 4. 项目知识的创建时机

项目知识空间的创建时机明确为：

**项目立项审批通过后自动创建。**

不建议在项目草稿阶段创建，原因：

1. 会产生大量无效分类
2. 草稿项目往往反复修改
3. 正式项目知识应在立项通过后开始沉淀

因此规则为：

1. 立项前可准备项目资料，但不自动生成项目知识空间
2. 立项通过后由系统创建项目知识主分类及预制子分类
3. 后续项目知识统一归入该分类体系

---

## 5. 项目知识的角色边界

### 5.1 项目经理

项目经理是项目知识的默认治理责任人。

建议具备：

1. 查看全部项目知识
2. 新增项目知识
3. 编辑全部项目知识
4. 删除项目知识
5. 管理项目知识分类
6. 审批项目知识借阅申请

### 5.2 项目成员

项目成员是项目知识的参与式维护者。

建议具备：

1. 查看全部项目知识
2. 新增项目知识
3. 编辑自己负责的项目知识
4. 不可删除项目知识
5. 不可管理项目知识分类
6. 不参与借阅审批

“编辑自己负责的项目知识”认定规则为：

1. `authorId` 命中当前用户
2. 或 `maintainerId` 命中当前用户

任一命中即可。

### 5.3 非项目成员

非项目成员默认不具备项目知识访问权限。

规则为：

1. 默认不可查看
2. 可通过借阅申请获得限时阅读权
3. 不可编辑
4. 不可删除
5. 不可管理分类

---

## 6. 项目知识的访问规则

### 6.1 默认访问规则

项目知识默认只对项目成员开放。

建议项目主分类默认配置：

1. `defaultVisibilityType = specified`
2. `defaultVisibleUserIds = 项目成员列表`
3. `managerUserIds = 项目经理`

这样项目成员创建文章时，可以默认继承当前项目成员可见范围。

### 6.2 项目成员变更的影响

当前阶段应明确：

1. 文章可见性更偏“创建时继承”模型
2. 项目成员后续变化，不一定自动回刷所有历史文章权限

因此后续需要补充成员变更同步机制，但第一阶段可以先接受这一模型。

### 6.3 访问与编辑是两回事

项目知识中，访问权限和编辑权限必须分开理解。

1. 项目成员默认可访问
2. 但项目成员不等于可编辑全部知识
3. 编辑仍需根据项目角色和文章责任人判断

---

## 7. 项目知识借阅规则

### 7.1 当前借阅机制事实说明

当前知识中心已经具备借阅能力，但借阅审批还没有接入工作流引擎。

当前实际机制为：

1. 用户提交借阅申请
2. 分类管理员直接审批
3. 支持通过、拒绝、撤销、到期
4. 审批人来自分类管理员配置
5. 不依赖 workflow 模块

因此，项目知识第一阶段借阅规则直接复用现有知识中心能力，不单独重做审批体系。

### 7.2 项目知识借阅默认策略

建议项目知识主分类默认开启借阅，并采用如下配置：

1. `allowBorrow = 1`
2. `borrowApprovalMode = catalogManager`
3. `managerUserIds = 项目经理`
4. `needBorrowReason = 1`
5. `maxBorrowDays = 7`

### 7.3 借阅审批流程

建议流程如下：

1. 非项目成员访问项目知识时无权限
2. 若该分类支持借阅，则显示借阅申请入口
3. 用户填写借阅时长和理由并提交申请
4. 项目经理作为分类管理员在借阅审批页处理申请
5. 审批通过后，用户获得限时阅读权限
6. 到期后权限自动失效

### 7.4 为什么当前不先接工作流

原因如下：

1. 当前知识中心借阅机制已经可用
2. 项目知识第一阶段需要先解决组织和权限问题
3. 若立刻接入工作流，会扩大范围并增加交付风险

因此当前策略为：

1. 先复用现有分类管理员审批
2. 等项目知识体系稳定后，再评估是否有必要接入工作流

---

## 8. 项目知识与项目管理的关系

### 8.1 项目知识是项目管理主线的一部分

项目知识不是知识中心单独做运营的内容，而是项目管理专项中的核心组成部分。

它与以下能力强相关：

1. 项目计划
2. 项目风险
3. 项目变更
4. 项目工单
5. 项目复盘

### 8.2 项目知识的回流路径

建议逐步形成以下沉淀路径：

1. 项目启动资料进入“项目概况”
2. 需求和方案进入“需求与方案”
3. 交付手册和培训材料进入“实施交付”
4. FAQ 和运维文档进入“运维支持”
5. 总结、经验、案例进入“项目复盘”

### 8.3 项目知识的经营价值

项目知识不只是给项目团队存资料，还具有以下价值：

1. 提升交付复用效率
2. 降低重复沟通成本
3. 为后续项目复盘提供依据
4. 为 AI 检索提供高价值语料

---

## 9. 项目知识对象规则

### 9.1 文章创建规则

建议规则：

1. 项目成员和项目经理可新增项目知识
2. 从项目页进入知识创建时，默认带入项目知识分类
3. 创建文章时默认继承项目知识分类的可见配置

### 9.2 文章编辑规则

建议规则：

1. 项目经理可编辑全部项目知识
2. 项目成员仅可编辑 `authorId` 或 `maintainerId` 命中的知识
3. 非项目成员不可编辑

### 9.3 文章删除规则

建议规则：

1. 项目经理可删除项目知识
2. 项目成员不可删除项目知识
3. 非项目成员不可删除

### 9.4 分类管理规则

建议规则：

1. 项目经理可管理本项目知识分类
2. 项目成员不可管理分类
3. 非项目成员不可管理分类
4. 根分类“项目知识”仍由知识中心统一治理

---

## 10. 实施阶段建议

### 10.1 第一阶段

目标：项目知识分类和借阅规则先跑通。

建议完成：

1. 项目知识主分类自动创建
2. 预制子分类生成
3. 项目成员可见规则落地
4. 项目经理借阅审批规则落地

### 10.2 第二阶段

目标：项目知识真正进入项目执行闭环。

建议完成：

1. 工单转知识
2. 风险案例转知识
3. 变更总结转知识
4. 项目页知识摘要和快捷入口增强

### 10.3 第三阶段

目标：项目知识进入复用和智能阶段。

建议完成：

1. 项目知识模板化
2. 项目上下文知识搜索
3. AI 优先检索项目知识
4. 评估借阅审批工作流化

---

## 11. 当前不建议优先做的事项

为了保证第一阶段范围稳定，当前不建议优先投入以下内容：

1. 复杂借阅审批流程重构
2. 借阅审批立即接 workflow
3. 复杂分类授权策略
4. 跨项目知识多归属模型

当前最重要的是先把：

1. 项目知识空间建起来
2. 项目成员访问规则跑通
3. 项目经理审批借阅规则跑通
4. 项目知识在项目页中有稳定入口

---

## 12. 最终结论

项目知识应被视为项目管理专项中的核心资产能力，而不是知识中心的附属内容。

当前阶段最合理的策略是：

1. 依托知识中心分类体系承载项目知识
2. 在项目立项审批通过后自动创建项目知识空间
3. 由项目经理作为项目知识分类管理员
4. 项目成员查看全部项目知识，并维护自己负责的知识
5. 非项目成员通过现有借阅审批机制申请限时阅读
6. 暂不急于把借阅审批接入工作流，先保证项目知识体系稳定运行

只要这套规则稳定下来，项目知识就能自然成为项目计划、执行过程、复盘总结和后续 AI 检索之间的关键连接点。
