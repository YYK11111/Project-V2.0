# 项目权限矩阵方案

## 1. 文档目的

本文档用于明确项目管理专项中的权限模型、角色边界、对象级权限规则和后续落地方式，解决当前系统“菜单权限有了，但业务对象级权限还不够清晰”的问题。

本文档重点回答：

1. 项目管理中需要哪些角色
2. 每个角色分别能看什么、做什么
3. 菜单权限、按钮权限和业务对象权限之间如何分层
4. 项目知识、计划、风险、变更、工单等对象如何做权限控制
5. 后续研发应该如何逐步落地

---

## 2. 权限建设目标

项目权限建设的目标不是让权限模型尽可能复杂，而是让系统在以下方面足够清晰：

1. 谁能看到某个项目
2. 谁能修改项目核心信息
3. 谁能发起和管理项目内业务动作
4. 谁能查看、编辑、删除项目知识
5. 谁能审批项目知识借阅

同时需要明确：

1. 系统功能权限不能替代业务对象权限
2. 有页面入口权限，不代表能操作任意项目对象
3. 项目权限必须与项目成员角色强绑定

---

## 3. 权限模型的三层结构

建议项目管理专项统一采用三层权限模型：

### 3.1 第一层：系统功能权限

用于控制用户是否能进入某类页面或使用某类菜单功能。

例如：

1. 是否能看到项目管理菜单
2. 是否能进入知识中心页面
3. 是否具备工单管理页面入口

这一层解决“能不能进入系统某个功能区”的问题。

### 3.2 第二层：业务动作权限

用于控制用户是否具备某种通用动作能力。

例如：

1. 是否具备新增项目权限
2. 是否具备修改项目权限
3. 是否具备删除项目权限
4. 是否具备提交审批权限

这一层解决“在具备系统入口后，是否允许执行某类动作”的问题。

### 3.3 第三层：业务对象上下文权限

这是项目管理专项最关键的一层，用于判断用户是否能对“当前这个项目、当前这条知识、当前这个风险对象”执行动作。

例如：

1. 某人有知识编辑按钮权限，但是否能编辑本项目知识
2. 某人有项目修改权限，但是否能改这个项目
3. 某人有借阅审批权限，但是否能审批这个项目知识的借阅

这一层解决“是否允许操作当前业务对象”的问题。

---

## 4. 项目角色体系建议

结合当前项目成员模型，建议在项目管理专项中重点关注以下角色：

1. 项目经理
2. 交付经理
3. 技术负责人 / 实施负责人 / 测试负责人
4. 普通项目成员
5. 访客
6. 非项目成员

当前阶段不需要把所有角色都做成完全不同的权限体系，但至少要明确核心几类角色的权责边界。

---

## 5. 核心角色边界建议

### 5.1 项目经理

项目经理是项目管理专项的核心治理角色。

建议具备：

1. 查看项目全部信息
2. 修改项目核心信息
3. 维护项目成员
4. 维护项目里程碑和基线计划
5. 发起项目审批与结项流程
6. 查看并管理项目知识
7. 删除项目知识
8. 审批项目知识借阅
9. 关注项目风险、变更和关键工单

### 5.2 交付经理

交付经理通常与项目经理在管理侧有较强协同关系，但不一定具备完全相同的治理权限。

建议具备：

1. 查看项目全部信息
2. 查看项目计划和执行状态
3. 查看风险、变更、工单和知识
4. 可参与计划和执行管理
5. 是否允许修改项目主信息，可根据后续治理要求再细化

当前阶段可先视作“强查看、弱治理”角色。

### 5.3 负责人类角色

包括：

1. 技术负责人
2. 实施负责人
3. 测试负责人

建议具备：

1. 查看项目全部执行信息
2. 维护自己负责范围内的任务、风险、问题或知识
3. 不具备删除项目或调整项目关键基线的权限

### 5.4 普通项目成员

建议具备：

1. 查看项目内大部分信息
2. 查看项目知识
3. 新增并维护自己负责的项目知识
4. 查看并参与任务、工单、汇报、评论等执行行为
5. 不可删除项目知识
6. 不可修改项目核心基线信息

### 5.5 访客

建议定位为：

1. 只读访问
2. 可查看有限项目信息
3. 不具备编辑、删除和治理动作

### 5.6 非项目成员

建议定位为：

1. 默认不可查看项目内部对象
2. 若涉及项目知识，可通过借阅方式获取限时阅读权限
3. 不具备项目内治理和执行权限

## 6. 项目管理专项推荐权限矩阵

### 6.1 项目对象权限矩阵

| 角色 | 查看项目 | 修改项目基础信息 | 维护成员 | 提交立项/结项审批 | 维护基线计划 | 查看执行数据 |
|---|---|---|---|---|---|---|
| 项目经理 | 是 | 是 | 是 | 是 | 是 | 是 |
| 交付经理 | 是 | 视规则而定 | 否 | 否/有限 | 否/有限 | 是 |
| 负责人类角色 | 是 | 否 | 否 | 否 | 否 | 是 |
| 普通项目成员 | 是 | 否 | 否 | 否 | 否 | 是 |
| 访客 | 有限 | 否 | 否 | 否 | 否 | 有限 |
| 非项目成员 | 否 | 否 | 否 | 否 | 否 | 否 |

### 6.2 项目知识权限矩阵

| 角色 | 查看知识 | 新增知识 | 编辑全部 | 编辑本人负责 | 删除知识 | 管理分类 | 审批借阅 |
|---|---|---|---|---|---|---|---|
| 项目经理 | 是 | 是 | 是 | 是 | 是 | 是 | 是 |
| 交付经理 | 是 | 视规则而定 | 否 | 否/有限 | 否 | 否 | 否 |
| 负责人类角色 | 是 | 是 | 否 | 是 | 否 | 否 | 否 |
| 普通项目成员 | 是 | 是 | 否 | 是 | 否 | 否 | 否 |
| 访客 | 有限 | 否 | 否 | 否 | 否 | 否 | 否 |
| 非项目成员 | 否（借阅后可读） | 否 | 否 | 否 | 否 | 否 | 否 |

“编辑本人负责”的认定规则建议统一为：

1. `authorId` 命中当前用户
2. 或 `maintainerId` 命中当前用户

任一命中即可。

### 6.3 执行对象权限矩阵

| 角色 | 查看任务/风险/变更/工单 | 新增执行对象 | 修改自己负责对象 | 修改全部对象 | 删除对象 |
|---|---|---|---|---|---|
| 项目经理 | 是 | 是 | 是 | 是 | 是/有限 |
| 交付经理 | 是 | 是 | 是 | 视规则而定 | 否/有限 |
| 负责人类角色 | 是 | 是 | 是 | 否 | 否 |
| 普通项目成员 | 是 | 是 | 是 | 否 | 否 |
| 访客 | 有限 | 否 | 否 | 否 | 否 |
| 非项目成员 | 否 | 否 | 否 | 否 | 否 |

当前阶段这里不需要一次性把所有对象的细粒度规则都做完，但应先建立统一原则。

## 7. 规则设计建议

### 7.1 项目可见性规则

建议当前阶段采用相对直接的规则：

1. 项目成员可见项目
2. 项目经理和交付经理默认可见项目
3. 访客视项目配置决定是否可见
4. 非项目成员默认不可见

### 7.2 项目修改规则

建议项目基础信息修改优先收口到项目经理。

原因：

1. 项目基础信息会影响审批、计划、驾驶舱、知识归属等多个对象
2. 如果修改权限过于分散，后续治理成本很高

### 7.3 执行对象修改规则

建议采用“项目经理全局管理，责任人按对象维护”的思路：

1. 项目经理可全局管理
2. 对象责任人可维护自己负责的对象
3. 普通成员仅维护自己负责或自己创建的对象

当前系统已进一步落地为：

1. 项目经理：对项目内任务、风险、变更、工单拥有全局编辑和全局删除权限
2. 交付经理：对项目内任务、风险、变更、工单拥有全局编辑和全局删除权限
3. 负责人类角色（技术负责人 / 实施负责人 / 测试负责人）：对项目内任务、风险、变更、工单拥有全局编辑权限，但不具备全局删除权限
4. 任务负责人 / 风险负责人 / 变更申请人 / 工单处理人 / 工单提交人 / 创建人：可编辑并删除自己归属的对象
5. 普通成员：仅可查看，不具备全局编辑或删除权限

### 7.4 知识对象删除规则

建议项目知识删除权先收口到项目经理。

原因：

1. 项目知识删除具备较强治理影响
2. 避免成员误删高价值知识资产

### 7.5 借阅审批规则

建议当前阶段统一为：

1. 项目经理审批项目知识借阅
2. 交付经理暂不作为默认审批人
3. 非项目成员只能通过借阅获取阅读权

## 8. 当前阶段落地建议

### 8.1 第一阶段：先做关键对象权限

优先收口：

1. 项目对象权限
2. 项目知识权限
3. 借阅审批权限

### 8.2 第二阶段：再做执行对象权限统一

逐步统一：

1. 任务权限
2. 风险权限
3. 变更权限
4. 工单权限

### 8.3 第三阶段：形成可复用权限模式

后续可将项目管理专项中验证有效的权限规则抽象成统一模式，服务其他业务域。

## 9. 当前已落地权限现状

以下内容不是规划，而是当前仓库中已经实现的权限行为。

### 9.1 项目对象权限

当前已落地的项目对象级权限包括：

1. 项目列表按可见范围过滤
2. 项目驾驶舱按可见范围过滤
3. 项目详情按对象级查看权限校验
4. 项目保存/更新按对象级编辑权限拦截
5. 项目归档按对象级权限拦截
6. 项目立项审批按对象级权限拦截
7. 项目结项审批按对象级权限拦截
8. 项目删除按对象级权限拦截

当前项目对象的可见与操作规则：

1. 全量权限用户：可查看和管理全部项目
2. 项目经理：可查看、编辑、归档、删除、发起立项/结项审批
3. 交付经理：当前具备项目查看权限，不具备项目核心信息全局修改权限
4. 普通项目成员：可查看，不可修改项目核心信息
5. 非项目成员：不可查看项目详情

### 9.2 项目可见范围规则

当前后端已真实执行以下规则：

1. 项目负责人可见自己负责的项目
2. 项目成员可见自己参与的项目
3. 具备 `*` 或 `business/projects/manageAll` 的用户可见全部项目

该规则目前已同时作用于：

1. 项目列表
2. 项目驾驶舱
3. 项目详情页数据读取

### 9.3 执行对象权限

当前后端已经统一了任务、风险、变更、工单的可见与编辑规则。

#### 任务

1. 可见：必须能看到任务所属项目
2. 可编辑：项目经理、交付经理、负责人类角色、任务负责人、创建人
3. 可删除：项目经理、交付经理、任务负责人、创建人

#### 风险

1. 可见：必须能看到风险所属项目
2. 可编辑：项目经理、交付经理、负责人类角色、风险负责人、创建人
3. 可删除：项目经理、交付经理、风险负责人、创建人

#### 变更

1. 可见：必须能看到变更所属项目
2. 可编辑：项目经理、交付经理、负责人类角色、变更申请人、创建人
3. 可删除：项目经理、交付经理、变更申请人、创建人

#### 工单

1. 可见：必须能看到工单所属项目
2. 可编辑：项目经理、交付经理、负责人类角色、工单处理人、工单提交人、创建人
3. 可删除：项目经理、交付经理、工单处理人、工单提交人、创建人

### 9.4 前端权限态同步

当前前端已经开始同步对象级权限态，而不再只依赖按钮权限：

1. 执行对象列表页根据后端返回的 `canEdit` / `canDelete` 控制“修改/删除”按钮显示
2. 执行对象详情页在提交前根据后端返回的 `canEdit` 提示是否允许编辑
3. 项目详情页根据项目对象级权限上下文控制“编辑项目”“提交结项申请”等关键按钮

### 9.5 知识权限

当前项目知识权限已独立成型：

1. 项目经理：可查看、编辑、删除全部项目知识，并审批借阅
2. 项目成员：可查看全部项目知识，可编辑自己负责的知识
3. 非项目成员：默认不可查看，仅能通过借阅获得限时阅读权限

### 9.6 提醒权限

当前项目提醒权限采用三层控制：

1. 系统级提醒策略
2. 角色级接收策略
3. 用户个人提醒偏好

默认规则为：

1. 间隔 24 小时提醒
2. 项目经理接收
3. 交付经理接收
4. 消息中心渠道开启

## 10. 技术落地建议

### 9.1 后端优先级高于前端隐藏

必须明确：

1. 前端隐藏按钮只能改善体验
2. 真正权限控制必须由后端接口校验完成

### 9.2 建议的校验顺序

后端校验时建议按以下顺序：

1. 是否具备系统功能权限
2. 是否具备业务动作权限
3. 是否具备当前对象上下文权限

### 9.3 建议优先抽象的校验能力

1. 是否为项目成员
2. 是否为项目经理
3. 是否为项目知识责任人
4. 是否为项目知识分类管理员

这些判断一旦统一，后续多个对象就可以复用。

## 11. 最终结论

项目权限矩阵的核心不是把角色做得越多越好，而是把“谁能看、谁能改、谁能管、谁能批”这四类关键边界稳定下来。

当前阶段最重要的是：

1. 把项目经理的治理权限收口清楚
2. 把项目成员的执行和知识维护权限边界明确清楚
3. 把非项目成员的访问边界和借阅路径明确清楚
4. 以后端对象级校验作为真正的权限基础

只要这套矩阵稳定下来，后续项目管理专项在知识、计划、执行、报表和治理上的建设就会更稳，也更容易形成统一体验。
