# 整个系统下一步规划路线图

## 1. 文档目的

本文档用于对齐当前系统下一阶段的整体建设方向，重点回答以下问题：

1. 当前系统处于什么阶段
2. 下一阶段的核心目标是什么
3. 各业务条线应按什么顺序推进
4. 哪些能力适合优先投入，哪些能力应暂缓
5. 如何将项目管理、知识中心、工作流、消息和报表收口成一个可持续演进的业务平台

本文档偏产品和管理视角，主要用于方向共识、版本规划和跨团队协同，不替代详细技术设计文档。

---

## 2. 当前阶段判断

结合现有代码结构、业务模块分布和已落地能力，当前系统已经完成了从 0 到 1 的骨架搭建，正在进入从“可用”走向“成型”的阶段。

当前系统具备以下基础：

1. 项目管理主模块已具备基础能力
2. 任务、工单、里程碑、风险、变更、Sprint、用户故事等业务子模块已铺开
3. 工作流已接入项目、任务、工单、变更、客户等多个业务场景
4. 知识中心已具备分类、标签、权限、借阅、AI 检索预留能力
5. 驾驶舱和聚合视图已初步形成

但当前系统也存在明显问题：

1. 项目管理尚未成为统一工作台，更多还是项目台账和聚合展示
2. 多个业务模块虽已有 CRUD，但执行闭环不完整
3. 权限控制仍偏菜单和按钮级，业务对象级权限不足
4. 报表、预警、协作提醒和经营分析能力偏弱
5. 知识中心和项目管理尚未完全打通
6. 多模块之间已有数据，但缺统一治理口径

因此，下一阶段不应继续追求横向新增大量模块，而应优先围绕“主工作台、执行闭环、知识底座、治理统一”四个方向持续收口。

---

## 3. 下一阶段总目标

系统下一阶段的总目标可以概括为一句话：

**把当前分散可用的业务模块，收口成一个以项目为核心、以执行为主线、以知识为沉淀、以工作流和治理为保障的项目交付管理平台。**

拆解后包含五个目标：

1. 项目管理成为全系统最核心的业务入口
2. 任务、风险、变更、工单、里程碑等形成可追踪的执行闭环
3. 知识中心成为项目知识、交付知识和运维知识的统一底座
4. 工作流、消息、权限、报表形成统一治理框架
5. 为后续 AI 检索、知识复用和智能运营预留稳定基础

---

## 4. 总体规划原则

为避免系统继续碎片化，下一阶段建议遵循以下原则：

### 4.1 以项目为中心，而不是以模块为中心

后续所有核心业务能力都应优先考虑如何回收到项目上下文中。项目不是一张基础台账，而应成为任务推进、风险管控、变更评估、知识沉淀和审批流转的统一入口。

### 4.2 优先做闭环，而不是优先做页面数量

已有多个业务页面和表单，但真正的价值来自：

1. 是否能推动业务从发起到执行再到沉淀形成闭环
2. 是否能让管理者看得见问题
3. 是否能让执行者用起来顺畅

因此后续要少做孤立页面，多做模块联动和流程闭环。

### 4.3 优先做统一治理，而不是各模块各写一套规则

权限、提醒、审批、统计口径这些能力不能散落在各模块单独定义，否则后续维护成本会迅速上升。要尽快收口成统一规则框架。

### 4.4 先产品闭环，再智能化增强

AI 检索、推荐、问答有明确价值，但前提是基础业务结构和知识结构稳定。下一阶段仍应以业务闭环和知识治理为主，AI 属于增强项，不应抢占基础能力建设节奏。

---

## 5. 四条核心建设主线

下一阶段建议围绕四条主线持续推进：

1. 项目工作台主线
2. 执行闭环主线
3. 知识底座主线
4. 治理统一主线

下面分别展开。

---

## 6. 主线一：项目工作台

### 6.1 目标定位

把项目管理从“项目台账 + 看板聚合页”升级为“统一业务工作台”。

项目详情页未来应承载：

1. 项目基础信息
2. 项目阶段状态
3. 关键执行指标
4. 统一业务入口
5. 关键审批状态
6. 风险与变更焦点
7. 项目知识沉淀

### 6.2 为什么这条线优先级最高

当前系统虽然已有多个业务模块，但业务入口仍较分散。如果项目管理不能成为统一收口点，后续系统会出现以下问题：

1. 用户需要在多个模块间来回切换
2. 项目经理无法在一个视图下掌握全局
3. 知识、流程、执行信息无法沉淀为同一业务上下文

因此，项目工作台是下一阶段的第一优先级。

### 6.3 建设方向

#### 第一阶段

1. 在项目详情页补齐统一入口
2. 项目页可直接发起任务、风险、变更、工单、Sprint、项目知识
3. 增强摘要区，聚合逾期、待审批、高风险、即将到期里程碑等信息
4. 将项目知识正式整合进项目详情页

#### 第二阶段

1. 将项目级工时、汇报、成员负载整合到项目视角
2. 增加项目结项资料页和结项检查视图
3. 将项目知识、审批、风险和变更形成更强关联

#### 第三阶段

1. 补充项目计划视图和甘特能力
2. 增加项目健康度评分
3. 支持项目阶段复盘与阶段治理

### 6.4 预期收益

1. 提升项目经理的使用黏性
2. 降低系统学习成本
3. 让项目真正成为全系统的业务中心
4. 为后续报表和经营分析提供统一主轴

### 6.5 项目计划专项

当前路线图里虽然提到了里程碑、计划视图和甘特能力，但缺少对“项目计划”本身的单独说明。项目计划实际上是项目工作台能否成立的关键基础，应单独作为专项建设内容明确下来。

#### 6.5.1 当前系统现状

从现有项目表单和实体来看，系统在立项阶段已经采集了部分计划信息：

1. 项目开始时间
2. 项目结束时间
3. 项目预算
4. 至少一条里程碑计划

同时，当前前端表单支持手工新增多条里程碑，并不是只能维护一个里程碑，只是当前默认模板和页面呈现还没有把“项目计划”提升为独立能力。

也就是说，当前系统已有“计划要素”，但还没有形成真正的“项目计划体系”。

#### 6.5.2 计划应在什么时候制定

建议明确采用“两阶段计划”模式，而不是只在某一个时间点一次性完成全部计划。

**阶段一：立项审批前制定基线计划**

立项审批前必须先有一版基线计划，用于证明项目具备可执行性和资源边界。此阶段计划不追求极细，但必须完整覆盖关键承诺信息。

立项前基线计划建议至少包含：

1. 项目开始时间和目标结束时间
2. 关键里程碑计划
3. 初步预算
4. 初始项目团队和负责人
5. 项目范围边界和主要交付物

这部分计划的作用不是精细排产，而是支撑立项评审、资源判断和时间承诺。

**阶段二：立项审批通过后制定执行计划**

项目正式立项后，再把基线计划细化为执行计划。执行计划才是真正驱动日常推进和管理跟踪的计划。

立项后执行计划建议逐步补充：

1. 工作分解结构
2. 任务包和责任人
3. Sprint 或阶段划分
4. 任务依赖关系
5. 详细时间排期
6. 工时与资源安排
7. 风险缓冲和关键路径

因此，路线图中应明确：

1. 立项前必须有基线计划
2. 立项后必须补执行计划
3. 两者不是替代关系，而是递进关系

#### 6.5.3 为什么不能只放在立项后制定

如果把项目计划完全放到立项后再制定，会带来几个问题：

1. 立项审批阶段缺少时间和交付承诺依据
2. 难以判断预算和资源是否合理
3. 容易导致项目一立项就进入“边干边想”的状态

因此，立项前至少要有一版基线计划，这是项目成立的前提条件之一。

#### 6.5.4 为什么又不能在立项前一次性做得过细

如果要求立项前就把任务级执行计划全部做完，也不合理。原因包括：

1. 需求和资源在审批前往往还不稳定
2. 过细计划容易在审批通过后立刻失真
3. 会显著提高立项阶段的准备成本

因此，立项前计划应控制在“足够支撑决策”的粒度，而不是直接做到任务排产级别。

#### 6.5.5 路线图中的计划建设方向

建议将项目计划能力分三步建设：

**第一步：补齐立项基线计划能力**

1. 强化项目表单中的计划区
2. 明确开始时间、结束时间、关键里程碑、预算和交付物要求
3. 将里程碑计划从附属表格提升为立项必备信息

**第二步：补齐立项后的执行计划能力**

1. 在项目详情页增加计划视图
2. 建立里程碑与任务、Sprint 的关联关系
3. 支持项目级任务编排和阶段拆解

**第三步：补齐计划跟踪与偏差分析能力**

1. 甘特图或时间轴视图
2. 计划与实际偏差分析
3. 关键路径和延期预警
4. 里程碑达成率分析

#### 6.5.6 对整体路线图的影响

加入项目计划专项后，项目工作台主线应进一步明确为：

1. 先完成项目基线计划收口
2. 再完成项目执行计划收口
3. 最后做计划跟踪、偏差分析和甘特可视化

项目计划不应被视为“后续可选增强项”，而应被视为项目工作台建设中的核心主线之一。

## 7. 主线二：执行闭环

### 7.1 目标定位

把当前各个业务模块从“记录型页面”升级为“有推进、有联动、有反馈”的执行闭环系统。

重点对象包括：

1. 任务
2. 风险
3. 变更
4. 工单
5. 里程碑
6. Sprint

### 7.2 当前问题

当前多个模块虽然具备列表、表单、审批或聚合能力，但仍普遍存在以下问题：

1. 模块内部闭环不完整
2. 模块之间联动较弱
3. 项目视角无法完整展示执行状态
4. 缺少从问题到知识沉淀的回流机制

### 7.3 任务闭环方向

当前任务模块基础较好，已具备评论、汇报、工时、依赖、审批等能力。下一阶段重点不再是补单点字段，而是把任务执行信息上卷到项目层。

建议方向：

1. 项目页可直接看到任务汇报与工时汇总
2. 增加任务视图切换，如列表、看板、时间轴
3. 增加任务模板或标准任务包
4. 对长期无评论、无汇报、进度异常任务做提醒

### 7.4 风险闭环方向

当前风险模块已有基础列表和风险矩阵能力，但尚未形成从识别到应对再到关闭的管理闭环。

建议方向：

1. 增加风险升级机制
2. 支持风险转问题、转变更
3. 形成项目风险趋势分析
4. 支持风险关闭率、延期关闭率等统计

### 7.5 变更闭环方向

当前变更审批已接入工作流，但变更对项目执行面的影响还不够可视化。

建议方向：

1. 明确变更影响范围
2. 变更后提示影响成本、进度、里程碑、资源
3. 变更结论可沉淀为项目知识
4. 变更趋势进入项目和经营视图

### 7.6 工单闭环方向

当前工单更多偏问题记录和处理流转，尚未与知识沉淀充分打通。

建议方向：

1. 明确工单来源与类型
2. 支持工单升级、转缺陷、转知识
3. 将高频工单沉淀为 FAQ 或运维知识
4. 在项目视角中展示项目关键工单问题

### 7.7 预期收益

1. 项目执行过程更透明
2. 管理者能更早识别异常
3. 各模块不再是孤立台账，而是执行链路的一部分
4. 为报表、预警和知识沉淀提供可靠来源

---

## 8. 主线三：知识底座

### 8.1 目标定位

把知识中心从“内容管理后台”升级为“项目交付知识底座”。

它未来不只是知识文章页面，而应承载：

1. 项目知识
2. 实施交付知识
3. 运维支持知识
4. FAQ 与案例库
5. AI 检索基础数据

### 8.2 当前判断

知识中心已经具备较好的基础结构：

1. 分类树
2. 标签
3. 作者/维护人
4. 可见范围
5. 借阅申请与审批
6. AI 检索预留字段

因此知识中心不需要推倒重来，下一阶段重点应放在与项目管理的整合和知识运营收口。

### 8.3 优先方向

#### 第一阶段

1. 落地项目知识整合方案
2. 项目立项审批通过后自动创建项目知识空间
3. 项目经理负责项目知识治理和借阅审批
4. 项目成员维护本人负责的知识

#### 第二阶段

1. 增加项目知识模板
2. 支持工单转知识、变更转知识、复盘转知识
3. 在项目页中沉淀 FAQ 和复盘类知识

#### 第三阶段

1. 知识搜索按项目上下文收口
2. AI 检索优先命中项目知识，再补公共知识
3. 建立项目知识和公共知识的协同模式

### 8.4 预期收益

1. 项目经验可持续沉淀
2. 高价值交付知识不再散落
3. 提升复用率，减少重复沟通
4. 为后续智能问答与推荐提供基础

## 9. 主线四：治理统一

### 9.1 目标定位

在业务模块逐渐丰富的同时，尽快收口统一治理层，避免系统未来因为规则碎片化而失控。

治理统一主要包括四个方面：

1. 权限治理
2. 消息与提醒治理
3. 报表与指标治理
4. 数据模型与接口口径治理

### 9.2 权限治理方向

当前系统较多依赖菜单和按钮权限，但后续必须逐步走向业务对象级权限控制。

建议形成三层权限框架：

1. 系统功能权限
2. 业务动作权限
3. 业务对象上下文权限

例如：

1. 用户拥有知识编辑按钮权限，不代表能编辑任意项目知识
2. 还需要根据项目身份、文章责任人、分类上下文做业务判断

这类模式应逐渐沉淀为统一规则，而不是每个模块单独实现一套。

### 9.3 消息与提醒治理方向

当前工作流已有通知能力，但系统化提醒还不够完整。下一阶段建议逐步把项目预警、执行异常和待办通知收口成统一提醒体系。

建议优先支持：

1. 任务逾期提醒
2. 长时间未汇报提醒
3. 高风险提醒
4. 变更待审批提醒
5. 借阅待审批提醒
6. 项目里程碑预警

### 9.4 报表与指标治理方向

驾驶舱已初具雏形，但还缺少统一口径的经营与管理指标。

建议下一阶段逐步收口以下核心指标：

1. 项目健康度
2. 项目进度偏差
3. 项目成本偏差
4. 风险关闭率
5. 变更影响率
6. 成员负载率
7. 知识沉淀活跃度

这些指标不一定一开始全部成熟，但应尽快统一定义和口径归属。

### 9.5 数据模型治理方向

多个业务模块已有实体和聚合逻辑，但部分领域模型仍偏薄，未来会影响报表、权限和联动能力。

建议尽快明确：

1. 项目主数据边界
2. 成员主数据边界
3. 审批状态与业务状态的关系
4. 汇总字段与明细字段的来源口径
5. 接口返回数据的统一风格

## 10. 版本路线图建议

为了便于管理和跨团队沟通，建议将下一阶段建设拆成四个连续版本。

### 10.1 V1.1：项目工作台收口

版本目标：

把项目管理从“聚合展示”推进到“统一业务入口”。

建议纳入内容：

1. 项目知识整合
2. 项目页统一业务入口
3. 项目摘要增强
4. 项目知识权限闭环
5. 立项基线计划信息收口

版本价值：

1. 项目管理正式成为系统核心入口
2. 项目知识开始纳入主业务线
3. 项目经理使用路径明显收敛

### 10.2 V1.2：执行闭环增强

版本目标：

把任务、风险、变更、工单从记录型模块升级为执行闭环模块。

建议纳入内容：

1. 项目工时与汇报上卷
2. 风险升级与联动
3. 变更影响分析
4. 工单转知识
5. 立项后执行计划视图建设

版本价值：

1. 提升项目执行透明度
2. 建立跨模块联动能力
3. 为预警和经营分析准备数据基础

### 10.3 V1.3：治理与报表

版本目标：

把系统从“能用”推进到“能管理”。

建议纳入内容：

1. 权限治理细化
2. 消息与提醒统一
3. 驾驶舱指标统一
4. 关键报表落地
5. 计划与实际偏差分析

版本价值：

1. 管理视角更清晰
2. 系统治理边界更稳定
3. 业务运营数据开始具备管理价值

### 10.4 V2.0：智能化与复用

版本目标：

把知识中心、项目管理和 AI 检索串起来，进入智能增强阶段。

建议纳入内容：

1. 项目知识模板化
2. AI 按项目上下文检索
3. FAQ、复盘、上线手册等知识沉淀标准化
4. 后续再评估借阅审批接入工作流

版本价值：

1. 提升知识复用效率
2. 形成 AI 业务落地场景
3. 为长期平台化演进打基础

## 11. 优先级建议

若只能选择最值得优先投入的几个方向，建议按以下顺序推进：

1. 项目知识整合
2. 项目详情页统一业务入口
3. 项目工时与汇报上卷
4. 项目级权限闭环
5. 报表和预警体系

排序原因如下：

1. 先把项目变成统一主入口
2. 再把执行数据和知识沉淀挂到项目上
3. 最后补治理、报表和智能化能力

这样可以保证每一阶段都能看到可用价值，而不是把大量时间投入到用户暂时感知不强的底层工作上。

---

## 12. 管理建议

为了让下一阶段路线图真正落地，除了产品和研发任务之外，还建议在管理层面同步推进以下事项：

### 12.1 统一业务优先级

必须明确：项目管理是主线，知识中心整合是主线延伸，其他模块建设要优先服务项目主线，而不是各自独立扩张。

### 12.2 控制需求发散

下一阶段应控制新增零散页面和临时功能，避免打断主工作台和执行闭环的收口。

### 12.3 保持版本主题明确

每个版本都应有明确主题：

1. V1.1 做入口收口
2. V1.2 做执行闭环
3. V1.3 做治理与报表
4. V2.0 做智能增强

避免一个版本同时塞入大量互不关联的功能。

### 12.4 文档同步沉淀

随着项目知识整合推进，建议同步沉淀：

1. 业务规则文档
2. 权限矩阵文档
3. 数据口径说明
4. 路线图版本说明

这样既方便内部协作，也能降低后续迭代中的沟通成本。

---

## 13. 最终结论

当前系统已经具备较完整的基础框架，下一阶段的关键不在于继续增加模块数量，而在于完成以下收口：

1. 让项目管理成为统一主工作台
2. 让任务、风险、变更、工单形成执行闭环
3. 让知识中心成为项目交付和运维知识底座
4. 让权限、消息、报表和数据口径形成统一治理框架

如果按此路线推进，系统将逐步从“多个可用模块的组合”演进为“以项目为核心的交付管理平台”。

这将同时提升三个层面的价值：

1. 对执行层，使用路径更清晰，协作效率更高
2. 对管理层，状态更透明，预警更及时，经营判断更有依据
3. 对平台自身，知识沉淀更稳定，后续 AI 和智能化演进更容易落地

因此，下一阶段最重要的事情不是继续横向扩展，而是坚定围绕“项目主线、执行闭环、知识底座、治理统一”四条主线持续推进。
