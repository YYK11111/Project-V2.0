# 项目管理字段补齐清单第一版

## 1. 文档目的

本文档用于梳理项目管理体系当前字段现状、缺失字段、字段用途以及下一轮字段级权限建设所需的基础字段，作为后续数据模型补齐和字段组权限落地的依据。

本文档重点回答：

1. 当前项目管理体系已经有哪些字段
2. 还缺哪些关键字段
3. 哪些字段应优先在下一轮补齐
4. 哪些字段需要纳入字段级权限管控范围
5. 如何与系统级角色、项目角色和对象级权限融合

---

## 2. 总体原则

下一轮字段补齐不建议一次性把所有潜在字段都补完，而应遵循以下原则：

1. 优先补齐驾驶舱、健康度、提醒和权限治理直接依赖的字段
2. 优先补齐字段组权限所需的核心字段，而不是先做单字段颗粒度控制
3. 优先补齐可复用、可统计、可审计的字段
4. 避免只为页面展示补字段，尽量保证字段有明确业务归属

## 3. 当前字段现状概览

### 3.1 项目主表 `project`

当前已经具备：

1. 项目基础信息：名称、编号、负责人、描述、状态、类型、优先级
2. 时间信息：开始时间、结束时间
3. 基线计划：主要交付物、范围边界、计划说明
4. 结项资料：验收说明、交付清单、遗留问题、项目复盘、验收日期
5. 经营信息：预算、实际成本、客户、进度
6. 流程与知识：工作流实例 ID、知识分类 ID、审批状态、当前节点

### 3.2 项目成员表 `project_member`

当前已经具备：

1. 项目 ID
2. 用户 ID
3. 项目角色
4. 是否激活
5. 是否核心成员
6. 备注
7. 排序

### 3.3 任务表 `task`

当前已经具备：

1. 项目、Sprint、里程碑关联
2. 任务名称、编号、负责人、经办人、父任务
3. 开始时间、截止时间
4. 状态、优先级、进度
5. 描述、附件
6. 预估工时、实际工时、剩余工时
7. 验收标准、故事点
8. 工作流审批状态

### 3.4 里程碑表 `milestone`

当前已经具备：

1. 项目关联
2. 名称、描述
3. 计划完成日期、实际完成日期
4. 状态
5. 关联任务数、已完成任务数
6. 创建人
7. 交付物清单
8. 排序

### 3.5 Sprint 表 `sprint`

当前已经具备：

1. 项目关联
2. 名称、目标
3. 状态
4. 开始日期、结束日期
5. 容量、承诺故事点、完成故事点
6. 总任务数、已完成任务数
7. Scrum Master
8. 回顾总结

### 3.6 风险 / 变更 / 工单

当前这三类执行对象都已经具备比较完整的执行字段，并且已接入项目上下文、知识回流和权限控制。

### 3.7 知识文章表 `busiArticle`

当前已经具备：

1. 分类、标题、摘要、正文、纯文本切片
2. 知识类型、关键词、检索权重、AI 优先等检索元信息
3. 作者、维护人
4. 可见范围、角色可见、用户可见
5. 标签、排序、状态、发布时间

## 4. 下一轮优先补齐字段

以下字段建议作为下一轮的第一优先级。

### 4.1 项目主表 `project`

#### P0 必补字段

1. `departmentId`
   - 含义：所属部门
   - 价值：支撑组织维度筛选、驾驶舱分组、字段级权限

2. `category`
   - 含义：项目分类
   - 价值：支撑项目类型之外的更细管理分类

3. `tags`
   - 含义：项目标签
   - 建议类型：`json` 或 `simple-array`
   - 价值：支撑运营标签、看板筛选、经验复用

4. `planStartDate`
   - 含义：计划开始时间
   - 价值：与实际开始时间分离，为偏差分析提供基准

5. `planEndDate`
   - 含义：计划结束时间
   - 价值：支撑项目级计划/实际偏差分析

6. `actualStartDate`
   - 含义：实际开始时间
   - 价值：支撑执行偏差和项目过程审计

7. `actualEndDate`
   - 含义：实际结束时间
   - 价值：支撑结项分析与交付偏差统计

8. `currency`
   - 含义：币种
   - 价值：经营分析基础字段

9. `riskLevel`
   - 含义：项目整体风险等级
   - 价值：项目健康度与驾驶舱快速识别

10. `qualityLevel`
    - 含义：项目整体质量等级
    - 价值：质量维度治理和汇报

11. `spentHours`
    - 含义：累计消耗工时
    - 价值：经营分析、工时统计、健康度评估

12. `creatorId`
    - 含义：项目发起人
    - 价值：责任链清晰、流程追踪清晰

#### P1 增强字段

13. `phase`
    - 含义：当前项目阶段
    - 例如：立项、实施、验收、结项

14. `phaseStartDate`
15. `phaseEndDate`

16. `businessLine`
17. `industry`
18. `projectSource`

### 4.2 项目成员表 `project_member`

#### P0 必补字段

1. `joinDate`
   - 含义：加入项目时间
   - 价值：责任审计、提醒策略、历史追踪

2. `notificationEnabled`
   - 含义：是否接收项目提醒
   - 价值：为提醒治理提供项目级开关

3. `responsibilityScope`
   - 含义：成员作用域
   - 建议值：`project / task / risk / ticket / change / knowledge`
   - 价值：为下一轮角色分域治理做基础

#### P1 增强字段

4. `positionTitle`
   - 含义：岗位/职责补充名称

5. `leaveDate`
   - 含义：退出项目时间

6. `fieldPermissionGroup`
   - 含义：字段权限组
   - 价值：下一轮字段组权限落地的重要基础

### 4.3 任务表 `task`

#### P0 建议补齐

1. `plannedStartDate`
2. `plannedEndDate`
3. `actualStartDate`
4. `actualEndDate`

价值：

1. 支撑任务级计划/实际偏差分析
2. 为后续更强计划联动提供稳定字段

#### P1 建议补齐

5. `sourceType`
   - 例如：`baseline / change / adhoc`

6. `sourceId`
   - 关联变更或其他来源对象 ID

### 4.4 里程碑表 `milestone`

#### P0 建议补齐

1. `ownerId`
   - 含义：里程碑责任人

2. `delayReason`
   - 含义：延期原因

#### P1 建议补齐

3. `phase`
4. `changeImpactFlag`
5. `riskImpactFlag`

### 4.5 Sprint 表 `sprint`

#### P0 建议补齐

1. `ownerId`
   - 含义：Sprint 负责人

2. `delayReason`
   - 含义：Sprint 延期/偏差说明

#### P1 建议补齐

3. `changeImpactFlag`
4. `healthScoreSnapshot`

### 4.6 风险 / 变更 / 工单

建议优先补齐：

1. `knowledgeLinked`
2. `knowledgeArticleId`

价值：

1. 形成“业务对象 -> 知识”的稳定反查链路
2. 驾驶舱和详情页可以更自然展示知识沉淀结果

### 4.7 知识文章表 `busiArticle`

#### P0 必补字段

1. `sourceType`
   - 例如：`project_close_review / ticket / risk / change`

2. `sourceId`
   - 来源业务对象 ID

3. `sourceProjectId`
   - 来源项目 ID

4. `templateType`
   - 例如：`faq / review / implementationGuide / launchChecklist`

价值：

1. 知识回流可追溯
2. 模板使用可统计
3. 方便从知识反查业务对象

## 5. 字段级权限建议分组

下一轮不建议直接做单字段权限，而建议先做字段组权限。

### 5.1 项目基础组

建议包含：

1. 名称
2. 编号
3. 类型
4. 优先级
5. 描述
6. 分类
7. 标签
8. 所属部门

### 5.2 项目计划组

建议包含：

1. 计划开始/结束
2. 实际开始/结束
3. 基线计划说明
4. 主要交付物
5. 范围边界
6. 里程碑计划

### 5.3 项目经营组

建议包含：

1. 预算
2. 实际成本
3. 币种
4. spentHours
5. 客户

### 5.4 项目结项组

建议包含：

1. 验收说明
2. 交付清单
3. 遗留问题
4. 项目复盘
5. 验收日期

### 5.5 项目知识组

建议包含：

1. 项目知识查看
2. 项目知识创建
3. 项目知识编辑
4. 项目知识删除

## 6. 字段组权限建议

### 6.1 项目经理

1. 基础组：可编辑
2. 计划组：可编辑
3. 经营组：可编辑
4. 结项组：可编辑
5. 知识组：可管理

### 6.2 交付经理

1. 基础组：只读
2. 计划组：可编辑
3. 经营组：只读
4. 结项组：可编辑
5. 知识组：可管理执行类知识

### 6.3 负责人类角色

1. 基础组：只读
2. 计划组：部分可编辑
3. 经营组：不可见或只读
4. 结项组：只读
5. 知识组：可编辑执行类知识

### 6.4 普通成员

1. 基础组：只读
2. 计划组：只读
3. 经营组：不可见
4. 结项组：只读或不可见
5. 知识组：按知识权限处理

### 6.5 访客

1. 基础组：只读
2. 计划组：不可见
3. 经营组：不可见
4. 结项组：不可见
5. 知识组：可读

## 7. 与系统级角色 / 权限融合建议

下一轮建议采用四层权限模型：

### 第一层：系统级菜单 / 按钮权限

控制：

1. 能不能进入某个模块
2. 有没有通用动作入口

### 第二层：项目成员角色

控制：

1. 在当前项目里的身份
2. 是项目经理 / 交付经理 / 技术负责人 / 访客中的哪一种

### 第三层：字段组权限

控制：

1. 在当前项目里能不能看 / 改某类字段组

### 第四层：对象归属权限

控制：

1. 这个任务是不是你负责
2. 这个风险是不是你负责
3. 这个工单是不是你处理
4. 这条知识是不是你维护

11. `project.spentHours`

14. `project_member.responsibilityScope`
15. `busiArticle.sourceType`
16. `busiArticle.sourceId`
17. `busiArticle.sourceProjectId`
18. `busiArticle.templateType`

### 第二阶段：字段组权限第一版

建议先只做项目对象，不立刻扩到全部业务对象。

优先做：

1. 计划组
2. 经营组
3. 结项组

### 第三阶段：前端显示/编辑态

1. 不可见字段组隐藏
2. 可见但不可改字段组禁用

### 第四阶段：后端字段组保存校验

1. 比对本次变更字段
2. 判断当前角色是否有该字段组编辑权

## 10. 最终结论

当前项目管理体系的主流程、执行闭环、知识回流、权限治理已经较为完整，但要继续向字段级权限和更细治理推进，必须先补齐关键治理字段。

建议下一轮优先完成：

1. 项目主数据补齐
2. 项目成员治理字段补齐
3. 知识来源字段补齐
4. 项目字段组权限第一版

这样才能让系统从“对象级权限治理”平滑进入“字段级权限治理”。
