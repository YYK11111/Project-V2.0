# 项目知识整合方案

## 1. 背景与目标

当前系统中，项目管理模块与知识中心模块都已具备一定基础能力：

- 项目管理已有立项审批、项目详情、项目成员、项目驾驶舱等能力
- 知识中心已有文章、分类、标签、可见范围、借阅申请、分类管理员审批等能力
- 当前“项目文档”模块独立存在，但后续不再作为重点演进方向

本方案目标是将“项目资料沉淀”统一收口到知识中心，通过“项目知识分类”方式整合到项目管理中，形成统一的项目知识治理模型。

核心目标：

1. 不再继续扩展项目文档模块，统一由知识中心承载项目知识
2. 项目立项审批通过后，自动创建项目知识空间
3. 项目经理负责项目知识治理与借阅审批
4. 项目成员可查看项目知识，并维护自己创建或负责的知识
5. 非项目成员可通过现有借阅审批机制申请限时阅读
6. 为后续项目知识搜索、模板化沉淀、AI 检索预留结构

---

## 2. 现状分析

### 2.1 项目管理现状

当前项目管理模块已具备：

- 项目基础信息管理
- 立项审批与结项申请
- 项目详情页与驾驶舱
- 项目成员与里程碑维护
- 任务、风险、变更、Sprint 等业务聚合

但当前项目管理中尚未形成统一的知识沉淀入口，项目资料与经验总结没有纳入“项目工作台”。

### 2.2 知识中心现状

当前知识中心模块已具备：

- 知识文章管理
- 分类树管理
- 标签体系
- 可见范围控制
- 作者、维护人机制
- 借阅申请与分类管理员审批
- AI 检索元信息预留

当前借阅逻辑已实现完整业务闭环，但暂未接入工作流引擎。

### 2.3 当前借阅能力事实说明

知识中心借阅当前并非“工作流审批”，而是“分类管理员审批”。

现状如下：

- 用户可提交借阅申请
- 分类管理员可在借阅审批页面直接审批
- 审批结果包括：通过、拒绝、撤销、到期
- 借阅有效期由分类配置决定
- 暂未接入 workflow 模块

因此，项目知识第一阶段不需要依赖工作流审批，直接复用现有借阅能力即可。

---

## 3. 总体方案

### 3.1 总体思路

采用“项目知识分类”模式，而非“文章直接绑定项目”的主方案。

实现方式：

1. 在知识中心下建立统一根分类：项目知识
2. 项目立项审批通过后，自动为该项目生成一个项目主分类
3. 在项目主分类下，自动预制若干标准子分类
4. 项目页通过项目主分类进入知识中心
5. 所有项目知识文章统一归属于该项目知识分类体系
6. 权限以“项目身份 + 分类上下文 + 文章责任人”综合判断

### 3.2 方案优势

相比文章直接增加 `projectId` 的方式，本方案优势如下：

1. 复用现有知识中心的分类治理体系
2. 复用现有文章权限继承能力
3. 复用现有借阅审批能力
4. 知识结构更清晰，适合归档、治理和搜索
5. 便于后续做项目知识模板化与 AI 检索收口

## 4. 分类结构设计

### 4.1 根分类

系统统一维护一个根分类：

- 项目知识

该分类作为所有项目知识主分类的父节点。

### 4.2 项目主分类

每个正式立项通过的项目，自动生成一个项目主分类。

命名建议：

- 项目编号-项目名称

例如：

- PRJ-20260418-001-某某实施项目

命名规则优势：

1. 项目编号唯一，避免重名
2. 方便搜索、排序和识别
3. 即使项目名称调整，也能通过编号识别来源

### 4.3 项目预制子分类

项目主分类下自动生成以下标准子分类：

1. 项目概况
2. 需求与方案
3. 实施交付
4. 运维支持
5. 项目复盘

### 4.4 各子分类建议用途

#### 项目概况
用于沉淀：

- 项目背景
- 干系人说明
- 项目启动资料
- 范围边界说明
- 组织与职责说明

#### 需求与方案
用于沉淀：

- 需求澄清
- 蓝图方案
- 设计方案
- 业务规则说明
- 实施策略

#### 实施交付
用于沉淀：

- 部署手册
- 上线检查清单
- 培训资料
- 验收说明
- 交付文档

#### 运维支持
用于沉淀：

- FAQ
- 故障处理
- 操作说明
- 环境说明
- 日常支持记录

#### 项目复盘
用于沉淀：

- 阶段总结
- 项目复盘
- 风险案例
- 经验教训
- 可复用实践

## 5. 权限模型设计

### 5.1 权限角色定义

项目知识相关权限涉及三类人：

1. 项目经理
2. 项目成员
3. 非项目成员

### 5.2 项目经理权限

项目经理拥有完整治理权限，包括：

1. 查看全部项目知识
2. 新增项目知识
3. 编辑全部项目知识
4. 删除全部项目知识
5. 管理项目知识分类
6. 审批借阅申请

项目经理来源：

- 项目成员表中角色为 `ProjectMemberRole.manager`

### 5.3 项目成员权限

项目成员拥有协作维护权限，包括：

1. 查看全部项目知识
2. 新增项目知识
3. 编辑自己创建或自己维护的知识
4. 不允许删除知识
5. 不允许管理项目知识分类
6. 不参与借阅审批

“可编辑自己创建的知识”的认定规则：

- `authorId` 命中当前用户，允许编辑
- `maintainerId` 命中当前用户，允许编辑
- 两者任一命中即可

### 5.4 非项目成员权限

非项目成员默认不具备直接访问权限，包括：

1. 默认不可查看项目知识
2. 如项目知识分类开启借阅，可申请借阅
3. 借阅审批通过后，可限时阅读
4. 不允许编辑
5. 不允许删除
6. 不允许管理分类

### 5.5 权限矩阵

| 角色 | 查看 | 新增 | 编辑全部 | 编辑本人负责 | 删除 | 分类管理 | 借阅审批 |
|---|---|---|---|---|---|---|---|
| 项目经理 | 是 | 是 | 是 | 是 | 是 | 是 | 是 |
| 项目成员 | 是 | 是 | 否 | 是 | 否 | 否 | 否 |
| 非项目成员 | 否（借阅后可读） | 否 | 否 | 否 | 否 | 否 | 否 |

## 6. 借阅策略设计

### 6.1 借阅机制沿用现有能力

项目知识第一阶段直接复用知识中心现有借阅机制，不接入工作流。

审批流程为：

1. 非项目成员访问项目知识时发现无权限
2. 若分类允许借阅，则可发起借阅申请
3. 项目经理作为分类管理员审批
4. 审批通过后获得限时阅读权限
5. 借阅到期后自动失效

### 6.2 项目知识分类借阅配置建议

项目主分类建议默认配置：

- `allowBorrow = 1`
- `borrowApprovalMode = catalogManager`
- `managerUserIds = 项目经理用户 ID`
- `needBorrowReason = 1`
- `maxBorrowDays = 7`

建议理由：

1. 满足跨项目、跨部门临时查阅需求
2. 由项目经理控制访问边界
3. 避免长期权限泛化
4. 与现有知识借阅逻辑完全兼容

### 6.3 子分类借阅策略

第一阶段建议项目预制子分类直接继承主分类借阅策略，不做差异化。

后续若有业务需要，可再支持对子分类单独配置借阅策略。

## 7. 生命周期设计

### 7.1 创建时机

项目知识分类的创建时机为：

- 项目立项审批通过后自动创建

不建议在项目草稿保存时创建，原因：

1. 会产生大量无效分类
2. 草稿项目可能反复修改
3. 不符合“正式项目才沉淀正式知识”的业务原则

### 7.2 创建流程

当项目立项审批通过后，系统执行以下动作：

1. 检查项目是否已有知识分类
2. 检查知识中心根分类“项目知识”是否存在
3. 如不存在，则自动创建根分类
4. 创建项目主分类
5. 创建项目预制子分类
6. 回写项目的知识分类 ID
7. 后续项目知识统一归入该分类体系

### 7.3 幂等处理

自动创建逻辑必须具备幂等性：

1. 已有 `knowledgeCatalogId` 的项目不重复创建
2. 不能仅依赖分类名称判断是否已创建
3. 必须以项目字段上的分类 ID 作为唯一映射依据

## 8. 数据模型设计

### 8.1 项目表新增字段

建议在项目表新增字段：

- `knowledgeCatalogId`

用途：

1. 记录项目对应的知识主分类 ID
2. 支撑项目页面进入知识空间
3. 支撑后续项目知识统计与权限判断
4. 避免通过分类名称反查项目关系

### 8.2 文章模型第一阶段不新增项目字段

第一阶段不建议给文章实体新增 `projectId`。

原因：

1. 当前分类体系已足够承载项目知识上下文
2. 避免文章出现“按分类”和“按项目”双重入口
3. 降低改造范围
4. 保持知识中心结构的一致性

若后续确实需要跨项目复用、项目级全文统计，再评估是否增加扩展关系。

## 9. 后端实现规划

### 9.1 分类初始化服务

新增或补充一个项目知识分类初始化服务能力，职责包括：

1. 保证根分类“项目知识”存在
2. 创建项目主分类
3. 创建项目预制子分类
4. 配置分类默认权限与借阅属性

### 9.2 审批通过后的自动建分类挂载点

建议挂载在项目立项审批完成后的业务处理逻辑中。

原因：

1. 当前项目审批通过后的业务状态更新已在审批整合层处理
2. 这里最符合“正式立项后生成知识空间”的业务时机
3. 可避免在项目 CRUD 层引入审批状态判断

### 9.3 项目知识权限校验

需要新增“项目知识上下文”权限判断逻辑：

判断条件：

1. 当前文章是否归属于某项目知识分类
2. 当前用户是否是该项目成员
3. 当前用户是否是该项目经理
4. 当前用户是否命中 `authorId` 或 `maintainerId`

### 9.4 编辑权限校验规则

编辑权限建议按如下规则校验：

1. 若当前用户为项目经理，允许编辑
2. 若当前用户为项目成员，且 `authorId` 或 `maintainerId` 命中，允许编辑
3. 否则拒绝编辑

### 9.5 删除权限校验规则

删除权限建议按如下规则校验：

1. 若当前用户为项目经理，允许删除
2. 若当前用户为项目成员，拒绝删除
3. 若当前用户为非项目成员，拒绝删除

### 9.6 分类管理权限校验

项目知识分类管理权限建议按如下规则校验：

1. 项目经理允许管理本项目知识分类
2. 项目成员不允许修改项目知识分类
3. 非项目成员不允许管理项目知识分类
4. 根分类“项目知识”仍由知识中心治理后台统一管理

## 10. 前端实现规划

### 10.1 项目详情页整合知识入口

在项目详情页新增“知识”相关入口或 tab，支持：

1. 查看本项目知识
2. 快速新增项目知识
3. 跳转项目知识列表
4. 展示项目知识摘要

### 10.2 项目知识列表视图

项目页进入知识列表时，应默认定位到本项目知识分类。

建议支持：

1. 展示当前项目主分类下全部知识
2. 支持按预制子分类筛选
3. 支持查看文章详情
4. 支持项目内新增知识

### 10.3 知识编辑页增强

从项目页进入知识编辑页时，应支持：

1. 自动带入项目知识分类
2. 默认归档到当前项目知识体系
3. 根据用户身份控制保存、删除等操作按钮
4. 对无权限用户给出明确提示

### 10.4 项目页面的知识摘要

后续建议在项目页展示以下摘要信息：

1. 项目知识总数
2. 最近更新知识
3. 复盘类知识数量
4. FAQ 数量
5. 可借阅项目知识数量

## 11. 成员变更同步问题

### 11.1 当前潜在问题

现有知识中心更偏“创建时继承权限”，即：

1. 文章创建时继承分类默认可见用户
2. 项目成员后续变更，不一定自动反映到历史文章权限

因此会存在两个潜在问题：

1. 项目新增成员后，旧文章可能暂时不可见
2. 项目移除成员后，旧文章可能仍保留可见性

### 11.2 第一阶段处理策略

第一阶段建议先接受“继承式权限”模型：

1. 新建文章继承当前项目成员权限
2. 不强制回刷历史文章
3. 先完成项目知识空间建设

### 11.3 第二阶段优化方向

后续建议补充成员变更同步能力：

1. 项目成员变化时，自动刷新项目知识相关文章的可见用户
2. 或在访问时增加动态项目成员校验

建议优先采用“成员变更触发同步刷新”方式，而不是直接重写所有文章访问逻辑。

## 12. 分阶段实施计划

### 12.1 P0：项目知识空间打通

目标：完成项目知识空间的自动创建与入口收口

范围：

1. 项目表新增 `knowledgeCatalogId`
2. 初始化根分类“项目知识”
3. 项目立项审批通过后自动创建项目主分类

5. 主分类配置项目经理、项目成员可见范围与借阅属性
6. 项目详情页增加知识入口
7. 从项目页进入知识中心时默认定位到项目知识分类
8. 非项目成员可通过现有借阅逻辑申请阅读

### 12.2 P1：权限闭环

目标：完成项目知识编辑、删除、分类管理权限控制

范围：

1. 项目知识文章编辑权限校验
2. 项目知识文章删除权限校验
3. 项目知识分类管理权限校验
4. 前端根据身份控制操作按钮

### 12.3 P2：治理增强

目标：提升项目知识治理与使用体验

范围：

1. 项目成员变化时同步知识可见权限
2. 项目详情页知识摘要统计
3. 项目知识快捷模板
4. 按预制子分类快速新建知识
5. 项目知识搜索收口

### 12.4 P3：智能化演进

目标：增强知识复用与 AI 场景支撑

范围：

1. 项目知识模板化
2. FAQ、复盘、上线手册模板
3. AI 检索优先命中当前项目知识
4. 项目知识与公共知识联动检索

## 13. 风险与注意事项

### 13.1 权限边界风险

若只在前端隐藏按钮，而后端不做校验，会导致权限失效。

因此必须以后端权限校验为准，前端仅作为展示层控制。

### 13.2 成员变更同步风险

第一阶段若不做历史文章权限同步，成员变更后可能出现短期权限不一致，需要提前在需求上明确。

### 13.3 分类重命名风险

项目知识主分类名称若允许随意修改，可能导致治理混乱。

建议第一阶段项目主分类名称由系统生成，项目经理可调整展示名称需谨慎控制。

### 13.4 借阅审批非工作流风险

当前借阅审批为分类管理员直接审批，不是工作流。第一阶段这不是阻塞问题，但后续如果业务需要统一审批轨迹，可考虑再接入 workflow。

---

## 14. 最终结论

项目知识应统一由知识中心承载，而不是继续扩展独立的项目文档模块。

推荐以“项目知识分类”作为载体，形成以下闭环：

1. 项目立项审批通过后自动创建项目知识空间
2. 项目经理作为分类管理员，负责知识治理与借阅审批
3. 项目成员可查看全部项目知识，并维护自己创建或负责的知识
4. 非项目成员可通过现有借阅审批机制申请限时阅读
5. 项目知识按预制子分类沉淀，形成稳定的知识结构
6. 后续可逐步扩展为项目知识搜索、模板化沉淀和 AI 检索入口

该方案与当前系统结构兼容度高、改造风险低、演进路径清晰，适合作为项目管理与知识中心整合的正式方案。
