# 项目计划能力建设方案

## 1. 文档目的

本文档用于明确项目计划能力在整个系统中的定位、分阶段建设方式、核心对象关系和实施边界，重点回答以下问题：

1. 项目计划到底在什么时候制定
2. 立项前计划和立项后计划的区别是什么
3. 当前系统已有的计划能力有哪些
4. 后续项目计划能力应如何分阶段建设
5. 里程碑、任务、Sprint、工时和甘特图之间应如何衔接

本文档用于统一产品、研发和项目管理三方口径，为后续项目工作台、执行闭环和报表分析提供稳定基础。

---

## 2. 核心结论

项目计划不应只在一个时间点一次性完成，而应采用“两阶段计划”模式：

1. 立项审批前制定基线计划
2. 立项审批通过后制定执行计划

后续再在执行计划基础上补：

1. 计划跟踪
2. 计划偏差分析
3. 时间轴与甘特图可视化
4. 计划预警与经营分析

这意味着：

1. 立项前必须有计划，但不要求过细
2. 立项后必须补细计划，才能支撑执行推进
3. 甘特图不是项目计划的起点，而是项目计划成熟后的展示形式

---

## 3. 为什么必须分两阶段建设

### 3.1 如果立项前没有计划

如果项目在立项审批前没有一版可评审的计划，会出现以下问题：

1. 无法判断项目周期是否合理
2. 无法判断预算是否可接受
3. 无法判断关键交付节点是否明确
4. 无法判断负责人和团队配置是否成立
5. 立项审批会退化成只看项目名称和描述的形式审批

因此，立项前必须有一版基线计划。

### 3.2 如果立项前计划做得过细

如果要求在立项前就完成任务级别、工时级别和依赖级别的细计划，也会带来问题：

1. 审批前需求往往还不稳定
2. 资源和排期在审批前可能随时变化
3. 准备成本过高，影响立项效率
4. 过细计划在审批通过后很容易失真

因此，立项前只需要达到“足以支撑决策”的粒度。

### 3.3 如果立项后不继续补计划

如果项目立项通过后，不把基线计划继续细化成执行计划，也会带来问题：

1. 项目推进只能依赖人工口头同步
2. 任务、Sprint、工时和风险无法与计划形成对应关系
3. 甘特图和时间轴无法建立在稳定对象上
4. 后续无法进行偏差分析和延期预警

因此，立项后必须补执行计划。

---

## 4. 当前系统现状

从现有代码结构看，系统已经具备“基线计划雏形”，但尚未形成完整的项目计划体系。

当前已有能力：

1. 项目开始时间
2. 项目结束时间
3. 项目预算
4. 项目负责人
5. 项目成员初始化
6. 项目里程碑计划

当前不足：

1. 项目计划没有被明确定义为独立能力
2. 里程碑只是表单中的一个区块，不是完整计划体系
3. 立项前计划和立项后计划没有明确区分
4. 里程碑与任务、Sprint 尚未建立稳定关联
5. 没有计划偏差分析能力
6. 没有项目级计划视图和甘特视图

因此，当前最合适的方向不是重新造一套复杂计划系统，而是从现有字段和对象出发，逐步把计划能力收口成体系。

---

## 5. 项目计划的总体结构

建议将项目计划能力拆成四层：

1. 基线计划层
2. 执行计划层
3. 跟踪分析层
4. 可视化展现层

### 5.1 基线计划层

作用：用于立项审批、资源判断和时间承诺。

主要对象：

1. 项目开始时间
2. 项目目标结束时间
3. 关键里程碑
4. 初步预算
5. 项目负责人
6. 初始团队配置
7. 主要交付物与范围边界

### 5.2 执行计划层

作用：用于项目正式立项后的推进、分工和执行跟踪。

主要对象：

1. 里程碑
2. Sprint
3. 任务包
4. 负责人和执行人
5. 任务依赖
6. 工时与资源安排

### 5.3 跟踪分析层

作用：用于判断项目执行是否偏离计划。

主要能力：

1. 计划与实际时间对比
2. 里程碑延期识别
3. 项目进度偏差分析
4. 执行风险与计划偏差联动

### 5.4 可视化展现层

作用：让计划更直观地被理解和使用。

主要能力：

1. 时间轴视图
2. 计划视图
3. 甘特图
4. 关键路径和延期提醒

---

## 6. 两阶段计划的边界定义

### 6.1 立项审批前：基线计划

立项前基线计划的目标不是把任务排满，而是形成可评审的项目承诺。

建议立项前必须具备以下信息：

1. 项目开始时间
2. 项目目标结束时间
3. 关键里程碑及计划日期
4. 初步预算
5. 项目负责人
6. 初始项目成员
7. 主要交付物说明
8. 范围边界或项目描述

其中“关键里程碑”是立项前计划的核心承载对象。

### 6.2 立项审批通过后：执行计划

项目审批通过后，基线计划应细化为执行计划。

建议执行计划逐步补充以下内容：

1. 里程碑下的任务分解
2. 任务与 Sprint 的关系
3. 任务开始/结束安排
4. 任务负责人和执行人
5. 任务依赖关系
6. 预估工时和资源配置
7. 风险缓冲与关键路径

### 6.3 两者之间的关系

基线计划和执行计划不是两套独立体系，而是前后递进关系。

正确关系应为：

1. 基线计划定义项目承诺边界
2. 执行计划在基线计划基础上进一步细化
3. 后续所有跟踪、偏差分析和甘特图都应建立在执行计划上
4. 若执行计划明显偏离基线计划，需要形成项目层提示或变更机制

---

## 7. 项目计划对象关系设计

建议后续围绕以下对象关系构建计划能力。

### 7.1 项目

项目是计划能力的总容器，负责承载：

1. 基线计划边界
2. 执行计划汇总
3. 计划与实际偏差分析

### 7.2 里程碑

里程碑是计划体系中的一级关键节点，建议作为“项目计划”的第一层稳定对象。

作用：

1. 承载立项前关键承诺节点
2. 承接立项后任务分组
3. 支撑项目时间轴和预警

### 7.3 Sprint

Sprint 适合承载执行阶段的节奏化推进，不一定适用于所有项目类型，但在研发和实施项目中具有较强价值。

建议关系：

1. Sprint 从属于项目
2. Sprint 可与里程碑形成阶段关联
3. 任务可归属到某个 Sprint

### 7.4 任务

任务是执行计划的最小行动对象。

建议关系：

1. 任务属于项目
2. 任务可归属里程碑
3. 任务可归属 Sprint
4. 任务可设置责任人、执行人、工时、依赖关系

### 7.5 工时与汇报

工时和汇报不是计划对象本身，但它们是计划跟踪的重要数据来源。

建议关系：

1. 工时和汇报挂在任务上
2. 任务汇总到项目层形成计划执行状态
3. 项目层再对比基线计划和执行计划形成偏差判断

---

## 8. 计划能力的建设阶段

建议将项目计划建设拆为三个版本阶段。

### 8.1 第一阶段：基线计划收口

目标：让立项前计划真正可用、可评审、可沉淀。

重点建设：

1. 强化项目表单中的计划区
2. 明确开始时间、结束时间、预算和里程碑为立项必填要素
3. 要求至少维护一条关键里程碑
4. 补充主要交付物或范围边界信息
5. 明确计划字段的业务含义，避免只是“填表项”

输出结果：

1. 项目立项时有一版可评审的基线计划
2. 立项审批不再只看描述，而是结合时间、里程碑和预算判断

### 8.2 第二阶段：执行计划视图建设

目标：让项目立项后可以形成可推进的执行计划。

重点建设：

1. 项目详情页增加计划视图
2. 建立里程碑与任务、Sprint 的关联
3. 支持项目阶段拆解和任务分配
4. 支持按阶段查看计划推进情况

输出结果：

1. 项目经理可在项目页查看执行计划
2. 执行计划与任务推进形成对应关系

### 8.3 第三阶段：偏差分析与甘特可视化

目标：让计划真正具备管理价值。

重点建设：

1. 计划与实际时间对比
2. 里程碑延期识别
3. 计划偏差预警
4. 甘特图和时间轴
5. 里程碑达成率分析

输出结果：

1. 项目计划从“静态记录”升级为“动态管理工具”
2. 管理层可以看到进度偏差和延期风险

---

## 9. 建议的字段与信息结构

### 9.1 基线计划建议最小字段集

项目层建议至少有：

1. 项目开始时间
2. 项目目标结束时间
3. 项目预算
4. 项目负责人
5. 项目主要交付物说明
6. 项目范围边界说明

里程碑层建议至少有：

1. 里程碑名称
2. 里程碑计划日期
3. 里程碑排序
4. 里程碑说明

### 9.2 执行计划建议增强字段集

里程碑层建议逐步补充：

1. 实际完成时间
2. 当前状态
3. 关联任务数量
4. 延期标识

任务层建议逐步补充：

1. 所属里程碑
2. 所属 Sprint
3. 计划开始时间
4. 计划结束时间
5. 责任人
6. 执行人
7. 预估工时
8. 任务依赖

### 9.3 偏差分析建议指标

1. 项目计划开始与实际开始偏差
2. 项目计划结束与预测结束偏差
3. 里程碑延期数量
4. 里程碑按时达成率
5. 关键任务延期数量
6. 计划工时与实际工时偏差

---

## 10. 与其他主线的关系

项目计划不是孤立能力，它与系统其他主线是强耦合关系。

### 10.1 与项目工作台的关系

项目计划是项目工作台的重要组成部分。如果没有计划，项目页只能看现状，无法判断未来路径和偏差。

### 10.2 与执行闭环的关系

任务、工单、风险、变更等执行数据要有计划基准，才能判断是否异常。

### 10.3 与治理和报表的关系

计划偏差、里程碑达成率、项目健康度等指标，都依赖项目计划对象稳定存在。

### 10.4 与知识底座的关系

项目计划的关键节点、阶段总结、延期原因、复盘结论等内容，也应逐步回流到知识中心沉淀。

---

## 11. 当前不建议优先做的内容

为了避免范围过大，以下内容当前阶段不建议优先投入：

1. 高复杂度资源排产系统
2. 过细的人天级排班系统
3. 多项目联动排程优化
4. 复杂关键路径自动计算引擎

当前更合理的策略是：

1. 先把基线计划做实
2. 再把执行计划视图做出来
3. 再做偏差分析和甘特图
4. 最后再评估是否需要更复杂的排产能力

---

## 12. 实施建议

### 12.1 产品侧

1. 明确基线计划和执行计划的业务定义
2. 明确立项前必须具备的计划字段
3. 明确不同项目类型的默认里程碑模板

### 12.2 后端侧

1. 稳定项目和里程碑模型
2. 补齐执行计划所需的对象关联
3. 为偏差分析和计划视图预留接口结构

### 12.3 前端侧

1. 强化项目表单中的计划区
2. 在项目详情页中新增计划视图
3. 后续按阶段增加时间轴和甘特图

### 12.4 管理侧

1. 立项审批必须审计划，不只审描述
2. 立项后必须补执行计划，不可长期停留在粗计划状态
3. 项目计划变更要能与风险、变更和复盘形成联动

---

## 13. 最终结论

项目计划能力不是项目管理中的附属项，而是项目工作台成立的核心基础之一。

正确建设顺序应为：

1. 立项前建立基线计划
2. 立项后细化执行计划
3. 在执行计划基础上补偏差分析
4. 最后用时间轴和甘特图提升可视化能力

因此，后续系统建设中应明确：

1. 项目计划从立项前就开始制定
2. 但立项前制定的是基线计划，不是完整执行计划
3. 立项审批通过后，再把基线计划演进为执行计划
4. 项目计划能力应与项目工作台、执行闭环、治理报表同步推进

只要按这个顺序推进，项目计划就能既支撑立项决策，又服务执行跟踪，还能为后续预警、报表和智能分析提供稳定基础。
