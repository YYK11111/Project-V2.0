# 整个系统开发实施优先级清单

## 1. 文档目的

本文档用于将《整个系统下一步规划路线图》进一步转换为可执行的研发实施清单，重点解决以下问题：

1. 哪些建设项必须优先投入
2. 每个版本建议包含哪些范围
3. 各条线之间的依赖关系是什么
4. 前端、后端、数据和联调应如何协同推进
5. 哪些能力适合当前阶段做，哪些能力应延后

本文档偏研发落地视角，适合用于排期、拆解任务、明确版本边界和安排协作顺序。

---

## 2. 优先级判断原则

为避免需求发散和版本目标失焦，建议后续研发排期统一遵循以下优先级原则：

### 2.1 优先支持项目主线

所有高优先级建设项应优先服务于“项目工作台”和“项目执行闭环”。

如果一个需求无法增强项目主线，就应降低优先级，避免系统继续横向发散。

### 2.2 优先做闭环，不优先做页面数量

同等投入下，应优先选择能形成业务闭环的事项，例如：

1. 项目知识整合
2. 项目工时和汇报上卷
3. 风险和变更联动
4. 统一权限校验

而不是优先新增孤立页面或零散字段。

### 2.3 优先收口已有能力，而不是增加更多平行能力

当前系统已经有较多业务模块，下一阶段最需要的是把已有模块收口成统一体验，而不是继续新增大量平行模块。

### 2.4 优先做可复用底座

底座类能力一旦成型，可降低后续多个模块的重复开发成本。重点包括：

1. 权限校验模式
2. 项目上下文聚合
3. 分类与知识整合机制
4. 统一消息与预警规则

---

## 3. 当前建议的优先级分层

建议将系统下一阶段需求划分为四层优先级。

### 3.1 P0：必须优先投入

P0 是直接决定系统主线是否成立的能力，优先级最高。

包括：

1. 项目知识整合
2. 项目详情页统一业务入口
3. 项目级权限闭环
4. 项目工时和汇报上卷
5. 项目基线计划收口

### 3.2 P1：主线增强项

P1 是在主线打通后立即补齐的能力，用于增强执行效率和管理视角。

包括：

1. 风险升级与联动
2. 变更影响分析
3. 工单转知识
4. 项目结项资料与复盘收口
5. 项目执行计划视图建设

### 3.3 P2：治理与经营项

P2 是在主线和执行闭环基本成型后，进一步补充治理和经营能力。

包括：

1. 消息与提醒统一
2. 驾驶舱指标统一
3. 核心报表落地
4. 成员变更与知识权限同步
5. 计划与实际偏差分析

### 3.4 P3：智能化增强项

P3 用于在基础业务稳定后推进复用和智能化。

包括：

1. 项目知识模板化
2. AI 项目知识检索
3. FAQ、复盘、上线手册标准化
4. 借阅审批工作流化评估

## 4. 版本建议与范围拆分

建议后续版本按以下顺序推进。

---

## 5. V1.1：项目工作台收口

### 5.1 版本目标

把项目管理从“聚合展示页”升级为“统一业务入口”，让项目页成为后续所有交付管理动作的核心入口。

### 5.2 建议纳入范围

#### 5.2.1 项目知识整合

1. 项目立项审批通过后自动创建项目知识分类
2. 自动创建项目预制子分类
3. 项目主分类默认配置项目经理和项目成员权限
4. 项目详情页增加知识入口
5. 从项目页进入知识中心时自动落到项目知识空间

#### 5.2.2 项目统一业务入口

1. 项目详情页补齐统一操作入口
2. 支持从项目页快速新建任务、风险、变更、工单、Sprint、项目知识
3. 统一入口和跳转路径，减少用户在多模块间切换成本

#### 5.2.3 项目摘要增强

1. 聚合逾期任务
2. 聚合待审批事项
3. 聚合高风险事项
4. 聚合即将到期里程碑
5. 聚合最近更新知识

#### 5.2.4 立项基线计划收口

项目计划不应完全放在立项后再做。V1.1 需要先把立项阶段的基线计划收口成标准化信息，作为项目立项和后续执行的共同起点。

建议纳入：

1. 强化项目表单中的计划区
2. 明确开始时间、结束时间、关键里程碑、预算和主要交付物要求
3. 将里程碑计划从附属表格提升为立项必备信息
4. 明确立项前计划用于评审，立项后计划用于执行

#### 5.2.5 项目知识权限闭环第一版

1. 项目经理可查看、编辑、删除全部项目知识
2. 项目成员可新增，并编辑自己负责的知识
3. 非项目成员通过现有借阅机制申请阅读
4. 后端真正校验项目知识操作权限

### 5.3 研发拆分建议

#### 后端

1. 项目实体新增 `knowledgeCatalogId`
2. 项目审批通过后自动创建知识分类
3. 项目知识上下文权限校验
4. 项目详情聚合接口补知识摘要
5. 项目基础计划信息的校验与结构收口

#### 前端

1. 项目详情页新增知识视图或入口
2. 项目详情页统一入口区改造
3. 知识编辑页支持项目上下文带入
4. 知识列表支持按项目知识分类定位
5. 项目表单计划区增强

#### 数据与规则

1. 明确项目知识主分类命名规则
2. 明确项目成员与项目经理判定规则
3. 明确项目知识借阅策略
4. 明确立项前基线计划字段边界

### 5.4 版本完成标准

1. 项目立项通过后能自动生成项目知识空间
2. 项目详情页成为主要业务入口
3. 用户无需反复切换模块即可发起核心业务动作
4. 项目知识权限可用且后端已真正拦截
5. 立项前基线计划信息完整且可支撑审批判断

---

## 6. V1.2：执行闭环增强

### 6.1 版本目标

把任务、风险、变更、工单等能力从“记录型模块”推进到“有联动、有反馈、有沉淀”的执行闭环系统。

### 6.2 建议纳入范围

#### 6.2.1 项目工时与汇报上卷

1. 在项目视角展示任务汇报与工时统计
2. 展示近期未汇报任务
3. 展示成员工作负载和协作提醒
4. 补项目层执行透明度指标

#### 6.2.2 风险联动增强

1. 风险升级机制
2. 风险转问题或转变更
3. 风险趋势分析
4. 风险关闭率统计

#### 6.2.3 变更影响分析

1. 增加变更影响范围展示
2. 明确变更对进度、成本、里程碑、资源的影响
3. 变更结论可沉淀为项目知识

#### 6.2.4 工单转知识

1. 高价值工单可沉淀为 FAQ 或运维知识
2. 支持典型工单转知识流程
3. 项目页可查看关键工单问题

#### 6.2.5 立项后执行计划视图建设

V1.2 开始把立项前的基线计划细化为真正驱动项目执行的执行计划。

建议纳入：

1. 在项目详情页增加计划视图
2. 建立里程碑与任务、Sprint 的关联关系
3. 支持阶段拆解、任务编排和责任人落位
4. 为后续甘特图和偏差分析打基础

### 6.3 研发拆分建议

#### 后端

1. 补项目层工时与汇报聚合接口
2. 风险升级、联动和统计接口
3. 变更影响分析字段与汇总逻辑
4. 工单转知识或知识关联逻辑
5. 项目执行计划视图所需的里程碑、任务、Sprint 关联数据

#### 前端

1. 项目详情页增加工时和汇报区块
2. 风险联动和变更影响展示增强
3. 工单转知识操作入口
4. 协作提醒和成员负载可视化
5. 项目执行计划视图

### 6.4 版本完成标准

1. 项目经理可在项目页看到执行透明度核心信息
2. 风险、变更、工单不再是独立记录页，而开始形成联动闭环
3. 业务问题能向知识沉淀回流
4. 项目已具备立项后执行计划视图和阶段化编排能力

---

## 7. V1.3：治理与报表

### 7.1 版本目标

把系统从“能用”推进到“能管理”，建立更稳定的治理体系和经营视图。

### 7.2 建议纳入范围

#### 7.2.1 权限治理细化

1. 收口业务对象级权限模式
2. 统一按钮权限与业务规则的边界
3. 明确项目、知识、任务等对象的上下文权限逻辑

#### 7.2.2 消息与提醒统一

1. 统一任务逾期提醒
2. 统一长时间未汇报提醒
3. 统一高风险提醒
4. 统一待审批提醒
5. 统一借阅审批提醒

#### 7.2.3 驾驶舱指标统一

1. 明确项目健康度指标
2. 明确进度偏差与成本偏差口径
3. 明确风险和变更类核心指标
4. 明确知识沉淀与活跃度指标

#### 7.2.4 报表落地

1. 项目健康度报表
2. 风险趋势报表
3. 变更影响报表
4. 成员负载报表
5. 知识沉淀活跃度报表

#### 7.2.5 计划与实际偏差分析

在基线计划和执行计划都具备后，V1.3 再做计划跟踪和偏差分析，避免前置投入过高。

建议纳入：

1. 计划与实际开始/完成时间对比
2. 里程碑延期识别
3. 项目计划偏差提示
4. 为甘特和经营分析提供偏差口径

### 7.3 研发拆分建议

#### 后端

1. 核心指标聚合接口统一
2. 统一消息与提醒服务能力
3. 权限规则抽象与复用
4. 报表查询和汇总接口
5. 计划偏差计算与统计接口

#### 前端

1. 驾驶舱指标视图统一
2. 报表页或报表卡片落地
3. 提醒中心与状态提示统一
4. 权限态按钮展示优化
5. 计划偏差视图和预警展示

### 7.4 版本完成标准

1. 管理层可以通过驾驶舱和报表获取核心项目经营信息
2. 关键业务异常能得到及时提醒
3. 权限边界不再依赖零散判断，而是逐步形成统一规则
4. 项目计划与实际偏差已可视化并可纳入预警

## 8. V2.0：智能化与复用

### 8.1 版本目标

在主线业务与治理框架基本稳定后，推动知识复用和智能化能力落地。

### 8.2 建议纳入范围

#### 8.2.1 项目知识模板化

1. 项目复盘模板
2. FAQ 模板
3. 上线手册模板
4. 培训资料模板

#### 8.2.2 AI 项目知识检索

1. AI 优先检索当前项目知识
2. 再补公共知识库
3. 项目上下文知识问答能力增强

#### 8.2.3 知识复用收口

1. 工单 FAQ 标准化
2. 复盘模板标准化
3. 项目经验和公共经验区分治理

#### 8.2.4 借阅审批工作流化评估

当前借阅审批已可用，但尚未接入工作流。V2.0 可再评估：

1. 是否需要统一审批轨迹
2. 是否需要更复杂借阅流程
3. 是否需要接入工作流实例与审批记录

### 8.3 版本完成标准

1. 知识沉淀有标准模板
2. 项目知识和公共知识形成协同检索能力
3. 智能化能力建立在稳定业务结构之上，而非凌空搭建

## 9. 条线依赖关系

为了避免排期冲突和返工，建议明确以下依赖关系：

### 9.1 项目知识整合是多个后续事项的前置条件

依赖项：

1. 项目页知识摘要
2. 工单转知识
3. 复盘模板沉淀
4. AI 项目知识检索

### 9.1A 项目基线计划是执行计划和偏差分析的前置条件

依赖项：

1. 项目执行计划视图
2. 甘特图和时间轴视图
3. 计划与实际偏差分析
4. 项目里程碑预警

### 9.2 项目工作台收口是执行闭环增强的前置条件

依赖项：

1. 工时和汇报上卷
2. 风险和变更联动入口
3. 项目级报表展示

### 9.3 权限治理是治理与报表统一的前置条件

依赖项：

1. 业务对象级权限控制
2. 驾驶舱可见范围控制
3. 知识与借阅治理

### 9.4 指标口径统一是报表落地和 AI 增强的前置条件

依赖项：

1. 经营驾驶舱
2. 趋势报表
3. 智能分析类能力

### 10.1 项目管理

1. 项目知识整合

4. 项目工时与汇报上卷
5. 执行计划视图

### 10.2 知识中心

优先级：最高

### 10.3 任务管理

### 10.4 风险管理

## 11. 当前不建议优先做的事项

为了保证主线聚焦，以下事项当前不建议优先投入：

1. 新增大量独立业务模块
2. 过早做复杂 AI 问答界面
3. 借阅审批立即接入工作流
4. 为所有模块同步重做 UI 风格
5. 过早做高度复杂的计划排产系统

这里需要特别说明：

1. 不建议当前阶段直接做高度复杂的排产系统
2. 但必须先做“立项基线计划 + 执行计划视图 + 偏差分析”的基础能力
3. 也就是说，应先把项目计划能力做实，再决定是否演进到更复杂的计划排产系统

这些事项并非不重要，而是不适合抢占当前阶段的主线资源。

---

## 12. 建议的研发协作方式

为了让上述优先级真正可执行，建议按条线组织协作：

### 12.1 主线推进方式

建议以“项目工作台”为主线组织需求评审和排期，而不是以模块负责人各自报需求的方式推进。

### 12.2 研发拆分方式

建议每个版本按以下维度同步拆任务：

1. 后端接口与模型
2. 前端页面与交互
3. 权限与业务规则
4. 消息与提醒
5. 联调与回归验证

### 12.3 验收方式

建议采用“用户路径验收”，即从项目经理和项目成员的真实操作路径出发验证，而不是只验单个页面是否可打开。

---

## 13. 最终建议

当前系统下一阶段最值得优先投入的方向不是新增更多业务模块，而是把已有模块收口成统一平台体验。

如果必须用一句话描述研发重点，应当是：

**先把项目工作台做实，再把执行闭环和知识底座挂上去，最后再补治理报表和智能化。**

建议后续研发排期严格围绕以下顺序推进：

1. V1.1 做项目工作台收口
2. V1.2 做执行闭环增强
3. V1.3 做治理与报表
4. V2.0 做智能化与复用

只要版本主题不跑偏、主线持续收口，系统就会从“多个功能模块的集合”逐步演进为“真正可管理、可协作、可沉淀”的项目交付管理平台。
