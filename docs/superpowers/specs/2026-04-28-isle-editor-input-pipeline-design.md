# Isle Editor 通用输入管道增强设计

## 目标

为 `nest-admin-frontend/src/features/isle-editor/**` 增加一套纯编辑器层的通用输入管道，统一处理以下输入来源：

- Markdown
- 网页 HTML
- 飞书等富文本 HTML
- Word / WPS 粘贴内容
- 纯文本

本次设计的核心目标不是保留来源应用的全部视觉样式，而是采用“结构优先、样式适度保留”的策略，让内容进入编辑器后：

- 标题、段落、列表、表格、代码块、引用、链接、图片等结构尽量正确
- 样式尽量收敛成编辑器自己的统一风格
- 不把业务模板、治理规则、知识中心专属逻辑带进编辑器内核

## 范围

本次设计覆盖：

- 编辑器粘贴输入的来源识别
- 输入内容的通用清洗
- 结构归一化为统一中间表示
- 中间表示写回当前 editor JSON
- Markdown / HTML / Office HTML / plain text 四类输入的统一处理策略
- 与输入管道相关的最小测试补充

本次不覆盖：

- 知识中心业务模板识别
- 发布前业务校验
- AI 自动整理或总结粘贴内容
- Office 原样视觉还原
- 复杂公式、复杂嵌套表格、流程图等重型导入能力
- 编辑器外层表单交互改造

## 已确认约束

用户已明确确认：

- 只做编辑器内核能力，不把业务逻辑混进来
- 优化重点是粘贴与输入体验
- 第一阶段采用“中间路线”：结构优先、样式适度保留
- 要优先覆盖全面兼容，而不是只针对某一种来源做深度特化

## 当前现状

当前编辑器已经具备：

- 结构化 JSON 文档协议
- 标题、列表、表格、引用、代码块、图片、视频、附件等节点能力
- 富文本编辑与查看态能力
- 媒体块上传与插入能力

但当前在输入侧还没有形成稳定统一的导入管道，主要问题是：

- 不同来源内容进入编辑器时，结构正确率依赖浏览器默认行为
- 富文本 HTML 很容易带入冗余样式、无意义标签、Office 私有属性
- Markdown、纯文本、HTML 缺少统一的中间转换层
- 输入能力目前更像多个局部行为叠加，而不是一个可复用的编辑器内核模块

## 方案对比

### 方案 A：轻量清洗层

做法：

- 保留现有编辑器输入方式
- 只在粘贴前后补一层 HTML 清洗
- 尽量让浏览器默认粘贴继续工作

优点：

- 改动小
- 上线快

缺点：

- 对 Markdown / plain text / Office HTML 的处理仍然是碎片化的
- 结构正确率不稳定
- 很难形成长期可复用的输入内核

结论：

- 不采用

### 方案 B：统一输入管道

做法：

- 所有输入先经过来源识别
- 再经过清洗层和结构归一化层
- 最后统一写成编辑器 JSON

优点：

- 符合“编辑器只做编辑器能力”的边界
- 结构最清晰，后续可扩展性最好
- 最适合同时覆盖 Markdown / HTML / Office / plain text

缺点：

- 比单纯清洗层改动大
- 需要明确设计中间表示

结论：

- 采用

### 方案 C：双模式输入

做法：

- 默认粘贴仍走轻量策略
- 额外提供“粘贴为 Markdown / 纯文本 / 保留格式”等显式入口

优点：

- 用户可控度高
- 复杂输入时更稳

缺点：

- 交互更重
- 不适合作为第一阶段主路径

结论：

- 第一阶段不采用，可作为后续增强方向

## 选定方案

选择方案 B：统一输入管道。

原因：

- 它最符合“编辑器通用能力”和“业务解耦”的方向
- 可以把所有来源输入统一收敛到编辑器标准结构，避免继续堆局部补丁
- 为后续其他页面复用编辑器输入能力打基础

## 总体策略

### 1. 结构优先

优先保住以下结构：

- 标题
- 段落
- 有序列表 / 无序列表
- 表格
- 代码块
- 引用块
- 链接
- 图片

如果来源样式和结构发生冲突，优先保住结构。

### 2. 样式适度保留

只保留有限白名单样式语义：

- 加粗
- 斜体
- 行内代码
- 基础链接
- 基础表格结构

不保留或主动清洗：

- 来源应用字号
- 来源应用颜色
- 冗余 `span`
- Office 私有 `class`
- 无意义 `style`
- 非必要的宽高与布局属性

### 3. 通用输入内核，不含业务

输入管道只负责把外部内容转换成标准编辑器文档，不负责：

- FAQ / 上线手册 / 复盘模板语义
- 知识分类与治理字段
- 业务发布校验

## 架构设计

建议拆成 4 个纯编辑器层单元。

### 1. `sourceDetector`

职责：

- 判断当前输入更接近哪类来源

识别结果：

- `markdown`
- `office_html`
- `html`
- `plain_text`

识别依据可以包括：

- Clipboard 中是否存在 `text/html`
- HTML 中是否包含 Office / WPS / Word 特征
- 文本中是否包含明显 Markdown 结构

### 2. `contentSanitizer`

职责：

- 对原始内容做最小必要清洗

能力：

- 去除无意义标签
- 去除冗余 `style` / `class`
- 保留允许标签白名单
- 清理空段落、嵌套垃圾节点
- 对 Office HTML 做额外清洗

输出仍然是来源相关内容，但已去掉脏样式和噪音。

### 3. `structureNormalizer`

职责：

- 把清洗后的内容统一转换成内部标准块结构

建议的中间结构节点：

- `heading`
- `paragraph`
- `bulletList`
- `orderedList`
- `blockquote`
- `codeBlock`
- `table`
- `image`
- `link`
- `text`

这层是整个输入系统的核心，不直接依赖业务页面。

### 4. `editorImporter`

职责：

- 把标准块结构转换成当前 `IsleContentDocument`
- 写回编辑器 JSON

要求：

- 输出必须符合当前 editor schema
- 对不支持的结构做合理降级，而不是原样塞入脏 HTML

## 各来源处理策略

### Markdown

第一阶段支持：

- 标题
- 段落
- 有序 / 无序列表
- 引用
- 代码块
- 分割线
- 表格
- 图片链接
- 普通链接

处理方式：

- 走独立 Markdown 解析路径
- 不先转成浏览器 HTML 再反推，减少不确定性

### 网页 HTML / 飞书 HTML

第一阶段目标：

- 结构尽量保真
- 样式收敛成编辑器统一风格

重点保留：

- 标题层级
- 段落
- 列表
- 表格
- 图片
- 链接
- 粗体 / 斜体 / 行内代码

重点清洗：

- 来源颜色与字号
- 冗余 `span`
- 无意义布局节点
- 粘贴产生的空段落

### Word / WPS

第一阶段目标：

- 不追求原样视觉还原
- 保住标题、列表、表格、段落、粗斜体结构

策略：

- 先识别为 `office_html`
- 在清洗阶段移除 Office 私有噪音
- 在结构归一化阶段优先抽取标准块结构

### 纯文本

第一阶段支持：

- 自动分段
- `-` / `*` / `1.` 列表识别
- fenced code block 识别
- URL 自动转链接

目标：

- 不让纯文本粘贴全部塌成一段

## 降级策略

当来源内容超出第一阶段支持范围时：

- 优先保留纯文本内容
- 保留可识别的基础结构
- 丢弃不可安全映射的复杂样式

宁可统一成干净文档，也不要把脏样式原样带入编辑器。

## 职责边界

### 编辑器输入层负责

- 粘贴来源识别
- 内容清洗
- 结构归一化
- 写回 editor JSON

### 业务页面不负责

- 手写 Office 清洗逻辑
- 手写 Markdown 解析逻辑
- 根据业务页面做粘贴分支处理

### 业务页面仍可负责

- 是否允许某类输入入口
- 是否在页面层做发布校验
- 是否使用业务模板

## 测试策略

至少补以下测试：

1. Markdown 标题、列表、代码块可被正确导入
2. 普通 HTML 标题、列表、表格可被清洗并导入
3. Office HTML 的冗余样式被清理，核心结构保留
4. 纯文本列表和 URL 能被识别
5. 不支持的复杂结构会合理降级为纯文本或基础段落

## 验收标准

满足以下条件视为第一阶段达成目标：

1. Markdown 直贴后能直接生成结构化文档
2. 网页 / 飞书 HTML 粘贴后不再带入大段脏样式
3. Word / WPS 粘贴时标题、列表、表格结构明显更稳定
4. 纯文本粘贴不会全部塌成一个段落
5. 所有输入最终都落到统一 editor JSON，而不是依赖来源应用原始样式

## 第一阶段不做事项

以下能力明确不纳入第一阶段：

- 粘贴策略切换弹窗
- 完整 Office 视觉保真
- 复杂公式与流程图导入
- 复杂嵌套表格精确兼容
- 业务模板识别与自动分类
- AI 自动整理粘贴内容

## 风险与取舍

### 风险 1：兼容面过大，第一版想做太全

取舍：

- 第一阶段以“结构正确率提升”为目标
- 不追求所有来源完全一致的视觉效果

### 风险 2：输入清洗过重，误删有价值信息

取舍：

- 采用白名单保留策略
- 对未知复杂样式优先降级，而不是强行保留

### 风险 3：业务方希望把模板逻辑塞进编辑器

取舍：

- 明确编辑器只负责通用输入能力
- 业务模板继续留在页面或业务适配层
