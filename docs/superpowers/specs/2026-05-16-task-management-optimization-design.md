# Task Management Optimization Design

## Goal

统一任务管理的状态流转、审批链路、权限判断、列表可见性和前端动作展示，消除“列表能点、详情不能改”“审批可重复发起”“状态与进度冲突”“看板与列表不一致”等问题。

## Current Problems

- `待完成审批(6)` 已出现在列表和部分页面，但看板分组没有完整收口。
- `submitApproval` 与 `submitCompletionApproval` 是两条不同链路，但前端和后端的状态闸门都不够硬。
- `list()` 与 `getOne()` 的可见性规则不完全一致，容易出现“列表看不到、详情能打开”。
- `canEdit / canManage / canExecute / canDelete` 的语义在列表页、详情页和接口层并未完全统一。
- 进度、延期、评论、汇报都依赖任务状态，但目前没有一张统一的动作矩阵。

## Status And Approval Model

任务主状态保持现有枚举：

- `1` 待处理
- `2` 处理中
- `3` 已完成
- `4` 已驳回
- `5` 暂缓
- `6` 待完成审批

审批状态保持现有枚举：

- `0` 未提交审批
- `1` 审批中
- `2` 已通过
- `3` 已驳回

规则约束：

- 普通任务审批只负责把任务从 `1` 流转到 `2` 或 `4`。
- 完成审批只负责把任务从 `2` 流转到 `6`，再由工作流回调回写为 `3` 或 `2`。
- `6` 是业务态，不是临时展示态，必须在列表、详情、看板、提醒、按钮和回调里统一处理。

## Permission Model

统一按任务返回四个能力字段：

- `canManage`
- `canExecute`
- `canEdit`
- `canDelete`

建议语义：

- `canManage`：项目管理者、任务负责人、任务创建人。
- `canExecute`：`canManage` 或任务经办人。
- `canEdit`：允许编辑任务基础信息，不等于所有操作权限。
- `canDelete`：允许删除任务，独立判断。

## Visibility Model

列表和详情必须共用同一套任务可见性规则：

- 项目可见范围
- 审批参与人可见范围
- 个人相关任务兜底可见范围

约束：

- 审批参与人可见任务不能被项目可见性过滤掉。
- 个人相关任务在没有项目可见范围时仍可见。
- `getOne()` 与 `list()` 对同一任务的可见性结果必须一致。

## Action Matrix

所有任务动作都必须满足“权限 + 状态”双校验。

- `save/update`：编辑权限 + 项目未归档
- `del`：删除权限 + 逐条校验
- `startTask`：仅 `1`
- `pauseTask`：仅 `2`
- `resumeTask`：仅 `5`
- `submitApproval`：仅 `1`，且不能重复发起
- `submitCompletionApproval`：仅 `2`，且不能重复发起
- `delayTask`：仅 `1/2/5/6`
- `updateProgress`：仅允许执行相关状态，禁止已完成/已驳回直接改

## Frontend Behavior

- 列表页只展示后端返回能力允许且状态允许的动作。
- 详情页按钮与列表页按钮必须使用同一套动作条件。
- “提交审批”和“提交完成审批”不能共享同一层判断。
- 任务状态、审批状态、当前节点文案必须在所有页面保持一致。
- `6` 必须显示为“待完成审批”，不能回退成数字。

## Non-Goals

- 不引入新的数据库字段。
- 不重构工作流引擎本身。
- 不改变现有任务审批的业务主线，只收口边界和幂等性。

## Verification Strategy

- 后端：覆盖状态闸门、权限判断、可见性、回调幂等、看板分组。
- 前端：覆盖按钮展示、状态文案、编辑/只读态切换。
- 统一执行后端 lint、后端单测、前端 type-check、前端结构测试。
