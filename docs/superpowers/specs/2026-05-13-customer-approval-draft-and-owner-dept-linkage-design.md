# Customer Approval Draft And Owner Department Linkage Design

## Goal

统一客户表单在“暂存/提交审批”场景下的交互语义，补齐销售负责人与所属部门的自动带出和联动逻辑，并把客户描述升级为与项目描述一致的富文本编辑体验。同时，把所有走审批业务模块的 `approvalStatus = '0'` 展示文案统一从“无需审批”调整为“未提交审批”。

## Current Context

- 客户表单 `nest-admin-frontend/src/views/business/crm/customerManage/form.vue` 当前已支持默认带出当前登录用户作为销售负责人，但所属部门仍为空。
- 客户表单底部主按钮仍是 `提交 / 取消 / 提交审批`，与项目表单的 `暂存 / 取消 / 提交审批` 模式不一致。
- 客户描述当前使用普通 `el-input textarea`，不是项目表单同款富文本。
- 项目表单 `nest-admin-frontend/src/views/business/projectManage/form.vue` 已有成熟模式：
  - 暂存和发起审批分成两条动作
  - 描述字段复用 `Editor` + `ViewRichText`
- 现有多个走审批业务页面和列表都把 `approvalStatus = '0'` 显示为“无需审批”。
- 后端工作流联动当前仍只在发起审批时把业务对象状态改成 `approvalStatus = '1'`，没有单独的“未提交审批”数据库状态值。

## Confirmed Scope

- 调整客户表单页 `nest-admin-frontend/src/views/business/crm/customerManage/form.vue`。
- 新增客户时：
  - 默认带出当前登录用户作为销售负责人
  - 默认带出当前登录用户所属部门
  - 底部显示 `暂存 / 取消 / 提交`
- 切换销售负责人时：
  - 自动把所属部门联动为所选销售负责人的所属部门
- 编辑客户时：
  - 初始加载继续使用接口返回值
  - 不在加载时自动覆盖已有负责人和部门
  - 仅当用户主动切换销售负责人时才联动所属部门
- 客户描述改为与项目描述一致的富文本编辑与查看方式。
- 所有走审批业务模块统一把 `approvalStatus = '0'` 的前端展示文案从“无需审批”改成“未提交审批”。

## Non-Goals

- 不新增新的审批状态值。
- 不重构工作流引擎或审批流转逻辑。
- 不把所有业务描述字段统一切到 Isle 编辑器。
- 不改造 `UserSelect` 组件的整体交互模式。
- 不在本次需求中扩大为“所有负责人字段都联动所属部门”的跨模块治理。

## Approaches Considered

### 方案 A：只改客户表单，不统一审批状态文案

做法：

- 客户表单实现默认部门、负责人切换联动、按钮文案调整、富文本描述
- 其他模块继续保留 `0 = 无需审批`

优点：

- 改动范围最小
- 风险最低

缺点：

- 不满足“所有走审批业务统一改文案”的明确需求

### 方案 B：客户表单改造 + 审批状态文案全局统一

做法：

- 客户表单实现所有交互改造
- 所有走审批业务页面和列表，把 `approvalStatus = '0'` 的展示文案统一为“未提交审批”
- 状态值仍沿用现有 `0/1/2/3`

优点：

- 满足业务期望
- 不引入新的状态值和工作流流转分支
- 可以复用现有按钮与审批模式

缺点：

- 需要排查多个前端文案映射点，防止漏改

### 方案 C：新增独立审批状态值表示“未提交审批”

做法：

- 后端新增新的审批状态值
- 前后端所有审批流转与展示一并调整

优点：

- 状态语义最严格

缺点：

- 改动面显著扩大
- 会牵涉数据库、工作流和历史状态兼容

### Recommendation

采用方案 B。

原因：它能满足当前需求，又保持状态值和工作流流转不变，风险显著低于新增审批状态值方案，同时比仅改客户表单更符合你的全局语义统一要求。

## Frontend Changes

### 1. 客户表单默认负责人和默认部门

客户表单初始化时补两个默认来源：

- `salesId` 默认取当前登录用户 id
- `deptId` 默认取当前登录用户所属部门 id

新增页进入时直接使用这组默认值。

若当前登录用户部门信息尚未恢复完成，则 `deptId` 允许暂时为空，后续由用户手动选择或由负责人切换联动补齐。

### 2. 销售负责人切换联动所属部门

联动规则：

- 仅在用户主动修改 `salesId` 时触发
- 根据当前选中销售负责人对应的用户对象读取部门信息
- 若该用户存在部门，则自动写入 `deptId`
- 若该用户没有部门，则清空 `deptId`

编辑页初始加载不触发自动覆盖，避免把已有客户部门数据在打开时意外改写。

### 3. 底部按钮语义统一

客户表单底部按钮统一调整为：

- `暂存`
- `取消`
- `提交`

按钮含义：

- `暂存`：保存客户，不发起审批
- `提交`：先保存客户，再发起审批

新增页和编辑页都使用这套主动作语义。

退回发起人等特殊审批动作按钮仍保留现有补充能力，但不再占用主按钮命名。

### 4. 客户描述切换为富文本

客户描述字段改为复用项目描述的已有实现：

- 编辑态使用 `Editor`
- 查看态使用 `ViewRichText`

不引入新的编辑器种类，也不切换为 Isle 编辑器。

## Approval Status Display Changes

### 1. 状态值语义保持不变

后端仍沿用现有值：

- `0`
- `1`
- `2`
- `3`

仅调整前端文案展示。

### 2. 全局展示文案统一

对于所有走审批业务的页面和列表：

- `0` 从“无需审批”改为“未提交审批”
- `1` 保持“审批中”
- `2` 保持“已通过”
- `3` 保持“已驳回”

若 `3` 且当前节点包含“退回发起人”，仍保留“已退回发起人”之类的细分展示，不被这次统一文案覆盖。

### 3. 适用范围

至少覆盖：

- 表单页中的审批状态展示
- 列表页中的审批状态列
- 详情页中直接映射 `approvalStatus` 的位置

本次重点排查已接入工作流审批的业务模块，例如：

- 客户
- 项目
- 任务
- 工单
- 变更

以及同类已接工作流的交付类单据页面。

## Data Flow

### 新增客户暂存

1. 用户进入新增客户页
2. 页面带出当前登录用户作为销售负责人
3. 页面带出当前登录用户所属部门
4. 用户编辑表单
5. 点击 `暂存`
6. 前端执行表单校验并调用保存接口
7. 保存成功后提示暂存成功

### 新增客户提交

1. 用户进入新增客户页
2. 页面带出默认负责人和部门
3. 用户编辑表单
4. 点击 `提交`
5. 前端先保存客户
6. 保存成功后发起客户审批
7. 后端把 `approvalStatus` 更新为 `1`
8. 前端提示提交成功

### 编辑客户切换负责人

1. 用户进入编辑页，加载现有客户数据
2. 表单显示接口返回的原负责人和部门
3. 用户主动改选销售负责人
4. 前端读取该负责人的所属部门
5. 自动覆盖 `deptId`

## Error Handling

### 当前用户缺少部门信息

若当前登录用户没有部门：

- 新增页默认 `deptId` 为空
- 不阻止页面初始化
- 由用户手动补选部门，或切换负责人后自动带出

### 选中负责人没有部门

若选中的销售负责人本身没有部门：

- 自动清空 `deptId`
- 不伪造默认部门
- 允许用户手动选择部门

### 提交审批前的校验

`提交` 行为需要先完成保存，因此：

- 先复用现有表单校验
- 保存失败则不发起审批
- 审批发起失败时应明确提示“客户已保存，但提交审批失败”或同等语义，避免误判为整单失败

## Risks And Boundaries

- 本次把 `approvalStatus = '0'` 全局显示为“未提交审批”，会改变已有用户对“无需审批”的认知。
- 由于不新增新的状态值，后端语义仍是沿用 `0`，本次统一本质上是前端展示语义收敛。
- 若后续业务需要区分“真的无需审批”和“尚未提交审批”，应另开需求引入新的状态值，而不是继续复用 `0`。
