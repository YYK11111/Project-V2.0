# Isle Editor 媒体块补齐设计

## 目标

补齐 `nest-admin-frontend/src/features/isle-editor/components/media-block/media-block.js` 在知识编辑器中的图片块、视频块、附件块能力，使其在编辑态、查看态、slash 插入、上传中、错误态、替换、删除、打开等链路上达到可用状态，并在整体风格上采用：

- 图片块偏 Notion
- 视频块与附件块的信息密度借鉴思源笔记

本次目标不是重新设计整个编辑器，也不是重做文章表单页，而是在已经接通真实 `isle-editor` 运行时的基础上，把三类媒体块补齐成完整能力。

## 范围

本次设计覆盖：

- `media-block.js` 的图片块、视频块、附件块主交互
- 图片、视频、附件节点与 `useIsleUpload.ts` 返回 attrs 的对齐
- 编辑态与只读态的媒体块展示一致性
- slash 插入、上传中、错误恢复、替换、删除、打开等行为
- 与媒体块相关的最小测试补充

本次不覆盖：

- 非知识页面编辑器行为改造
- 后端上传接口新增
- 媒体转码、缩略图生成、远端元信息探测
- 大范围重做文章页面整体布局

## 已确认约束

用户已明确确认以下约束：

- 三类媒体块一起补齐，不拆成三次实现
- 风格采用混合方案：整体像 Notion，但附件/视频的信息密度借鉴思源
- 不只是编辑页可用，还要覆盖查看态与整体工作流

## 当前现状

当前三类媒体块都已经接入统一的 `media-block.js`，具备以下基础：

- `image` / `video` / `attachment` 三种类型共用同一套组件
- 已支持本地文件选择
- 已支持手动输入 URL
- 已接入项目上传适配层 `useIsleUpload.ts`
- 已支持基础预览与删除、打开按钮

但当前仍然存在明显缺口：

- 编辑态与查看态的一致性不足
- 状态展示有基础，但不完整、不稳定
- 替换/重试/失败保留块的体验还不够成型
- 附件块仍偏“功能组件”，不够像知识块卡片
- 视频块的元信息与预览结构还不够完整

## 方案对比

### 方案 A：最小行为补齐

做法：

- 只补上传、替换、删除、打开、错误恢复
- 不明显调整块外观结构

优点：

- 改动最小
- 风险最低

缺点：

- 媒体块仍然像临时接线，而不是完整知识块
- 很难达到用户对 Notion / 思源混合体验的预期

结论：

- 不采用

### 方案 B：编辑态完整，查看态基础

做法：

- 编辑态补齐所有动作和状态
- 查看态先只保证可展示

优点：

- 编辑体验提升快

缺点：

- 编辑态和查看态割裂
- 知识内容发布后的阅读体验仍然断层

结论：

- 不采用

### 方案 C：三类媒体块全链路一次性补齐

做法：

- 编辑态、查看态、slash 插入、上传中、错误态、元信息、动作区一次性对齐

优点：

- 一次性形成完整知识编辑体验
- 三类块共用一套组件，集中补齐效率最高
- 不会在图片 / 视频 / 附件三条线上反复返工

缺点：

- 改动面最大
- 需要同时补测试与回归

结论：

- 采用

## 选定方案

选择方案 C：三类媒体块一起补齐。

原因：

- 图片、视频、附件当前都走同一套 `media-block.js` 和同一条上传/预览/动作链路
- 分开做只会反复修改同一层代码
- 你已经明确要求编辑、查看、上传、slash、状态等全链路都完整

## 统一设计原则

### 1. 统一块模型

- 图片、视频、附件继续共用 `media-block.js`
- 通过 `type = image | video | attachment` 分化预览区与信息区
- 不拆成三套独立组件，避免重复实现上传、状态、动作逻辑

### 2. 编辑 / 查看一致

- 编辑态与查看态使用同一套节点结构与主要视觉语言
- 编辑态保留操作区
- 查看态去掉编辑动作，但保留预览与元信息

### 3. 混合风格

- 图片块偏 Notion：大预览、弱边框、动作弱化
- 视频块与附件块偏思源：信息更完整、块感更强、操作区更明确

### 4. 状态完整

三类媒体块都必须覆盖：

- `idle`
- `uploading`
- `done`
- `error`

并保证：

- 失败时块不消失
- 重试在原块上进行
- 替换不会破坏块位置与上下文

## 三类媒体块的具体交互

### 图片块

编辑态结构：

- 上方：图片预览区
- 下方：轻量操作条
- 弱化元信息

编辑态动作：

- 替换
- 打开原图
- 删除
- 手动输入图片地址并确认
- 上传失败后重试

查看态要求：

- 保留大图预览
- 保留最小标题 / alt 信息
- 不显示编辑动作

### 视频块

编辑态结构：

- 上方：视频预览区 / poster
- 中间：标题、文件名、mime、大小、状态
- 下方：操作区

编辑态动作：

- 重新上传
- 打开源文件
- 删除
- 手动输入视频地址并确认
- 上传失败后重试

查看态要求：

- 直接可播放
- 保留标题 / 文件名
- 保留必要元信息

### 附件块

编辑态结构：

- 左侧：图标 / 类型标识
- 中间：文件名、扩展名、大小、mime
- 右侧或底部：动作区

编辑态动作：

- 打开
- 替换
- 删除
- 重试上传
- 手动输入 URL

查看态要求：

- 保持附件卡片，不退化成裸链接
- 至少展示文件名、扩展名、大小

## 职责划分

### `media-block.js`

负责：

- 预览区
- 信息区
- 动作区
- 本地文件选择
- URL 输入确认
- 替换、删除、打开、重试
- 上传中 / 错误态 / 完成态展示

不负责：

- 具体上传 API
- URL 规范化实现

### `useIsleUpload.ts`

负责：

- 调用项目 `/upload`
- 根据类型返回标准 attrs
- 图片 / 视频返回 `src`
- 附件返回 `url`
- 规范化 `/upload/`、`/static/`、绝对 URL

### `image.js` / `video.js` / `attachment.js`

负责：

- 节点 schema
- attrs 默认值
- parseHTML / renderHTML
- slash 菜单元信息
- 对应命令 `setImage` / `setVideo` / `setAttachment`

### `IsleArticleViewer.vue`

负责：

- 只读 runtime 外层容器
- 与查看态 DOM 约定保持一致

不负责：

- 编辑动作
- 上传行为

## 关键实现要求

### 上传返回值与节点 attrs 对齐

- `image` 节点：使用 `src`
- `video` 节点：使用 `src`
- `attachment` 节点：使用 `url`

所有类型都尽量补齐：

- `name`
- `size`
- `mime`
- `status`
- `error`

### slash 插入

必须继续支持：

- `/image`
- `/video`
- `/attachment`

插入后焦点仍留在当前块区域，便于继续上传 / 填 URL。

### 块稳定性

- 删除当前块只删除块本身
- 上传失败时保留块
- 替换时复用当前块，不删除重建

## 测试策略

### 组件层测试

需要补或增强：

- 图片上传成功 / 失败 / 重试
- 视频 URL / 文件两种模式
- 附件卡片展示与打开动作
- 替换行为
- 状态切换是否稳定

### 扩展层测试

需要补或增强：

- `image.js`
- `video.js`
- `attachment.js`

验证：

- attrs 默认值
- `renderHTML` 结果
- slash 元信息

### 页面层回归

继续验证：

- `aev` 相关
- `view` / `detail` 相关
- `IsleArticleViewer` 相关

## 风险与控制

### 风险 1：三类块分开修，造成同层反复返工

控制：

- 三类统一在 `media-block.js` 收口

### 风险 2：编辑态修好，但查看态仍不完整

控制：

- 查看态与编辑态同时验收

### 风险 3：上传 attrs 和节点 schema 不一致

控制：

- 统一由 `useIsleUpload.ts` 输出标准 attrs
- 扩展层与组件层都按这一约定实现

### 风险 4：块状态切换导致节点丢失或重复创建

控制：

- 块失败时不删除
- 替换在原块上更新 attrs

## 最终结论

本次不再把图片、视频、附件当成“能插入就行”的节点，而是作为知识编辑器中的完整媒体块统一补齐。整体风格采用：

- 图片块偏 Notion
- 视频块 / 附件块偏思源

并在编辑态、查看态、slash、上传中、错误恢复、元信息和动作区上一次性收口。这样媒体块才能真正成为知识正文的一部分，而不是临时拼接的上传控件。
