# 系统 Logo 与标签页图标失效修复设计

## 背景

当前系统配置页支持上传 `systemLogo` 和 `browserIcon`，并将上传结果保存到系统配置表中。

现状问题是：这两个文件通过通用上传接口进入 `sys_file` 后，状态为 `Pending`。系统配置保存时没有把它们标记为已关联，而后端存在每日凌晨执行的孤儿文件清理任务，会删除超过 24 小时仍处于 `Pending` 状态的文件。因此，系统 Logo 和标签页图标在保存数天后会因物理文件被清理而失效。

## 目标

1. 系统配置中使用的 `systemLogo` 和 `browserIcon` 不再被孤儿文件清理任务误删。
2. 替换系统 Logo 或标签页图标时，旧文件可以进入清理流程，不长期残留。
3. 保持前端上传与展示方式不变，避免扩大改动范围。
4. 配置保存过程对缺失文件记录、外链图片、空值场景具备容错能力。

## 非目标

1. 不重做通用上传组件。
2. 不新增专门的前端附件关联调用。
3. 不修改现有静态文件访问路径规则。
4. 不重构整套附件生命周期，仅修复系统配置相关链路。

## 方案选择

### 方案 A：在后端系统配置保存时自动关联附件

保存系统配置时，由后端识别 `systemLogo` 与 `browserIcon` 对应的上传文件，并将这些文件标记为已关联。

优点：

1. 根因修复，附件关联责任留在后端。
2. 与现有其他业务模块的附件管理模式一致。
3. 前端无需理解附件业务类型、关联时机、失败补偿。

缺点：

1. 需要为系统配置增加一层专用保存逻辑。

### 方案 B：前端保存后调用附件关联接口

优点：

1. 逻辑直观。

缺点：

1. 前端承担了不该承担的附件生命周期管理职责。
2. 容易出现“配置保存成功但附件关联失败”的不一致状态。
3. 后续新增配置附件字段时容易再次漏掉。

### 方案 C：新增系统配置专用上传接口

优点：

1. 领域边界清晰。

缺点：

1. 改动面过大，当前问题不需要引入新上传通道。

## 最终设计

采用方案 A：在后端系统配置保存逻辑中自动处理 `systemLogo` 与 `browserIcon` 的附件关联和旧文件清理状态。

### 数据流

1. 前端继续通过现有通用上传接口上传图片。
2. 上传接口继续返回相对路径并写入系统配置表单。
3. 用户点击保存后，请求进入系统配置保存接口。
4. 后端读取当前最新系统配置，提取旧的 `systemLogo` 与 `browserIcon`。
5. 后端保存新的系统配置记录。
6. 后端提取新配置中的 `systemLogo` 与 `browserIcon`，查找 `sys_file.storedPath` 对应记录。
7. 找到后，将这些文件更新为 `Associated`，业务类型标记为 `system_config`，业务 ID 记录为当前配置记录 ID。
8. 对于旧配置中已不再使用的文件，将其标记为 `Deleted`，交由现有清理任务按既有机制删除物理文件。

### 责任划分

#### 前端

1. 不改上传组件行为。
2. 不新增附件关联请求。
3. 继续只保存 `systemLogo`、`browserIcon` 的相对路径。

#### 后端

1. 为系统配置增加专用保存入口或重写现有保存逻辑。
2. 在保存完成后统一处理系统品牌图片附件的关联。
3. 负责旧附件的状态回收。

## 后端实现设计

### 1. 系统配置保存入口

当前 `system/configs` 直接复用基础 CRUD 保存逻辑。这里需要为系统配置增加显式保存方法，使配置保存后可以补充附件关联处理。

建议方式：

1. 在 `configs/controller` 中新增或覆盖保存接口。
2. 在 `configs/service` 中新增保存方法，内部顺序为：
   - 读取当前最新配置
   - 保存新配置
   - 同步品牌图片附件状态
   - 返回保存结果

### 2. 附件同步逻辑

在 `configs/service` 内新增一个仅服务于系统配置的附件同步方法，输入为：

1. 旧配置中的品牌图片路径集合
2. 新配置中的品牌图片路径集合
3. 当前保存后的配置 ID

处理规则：

1. 对新路径集合做清洗：
   - 去除空值
   - 去除外链地址
   - 去重
2. 根据新路径集合查询 `sys_file` 记录。
3. 将命中的记录更新为：
   - `status = Associated`
   - `businessType = system_config`
   - `businessId = 当前配置 ID`
4. 计算旧路径集合中“已被替换且不再使用”的文件。
5. 对这些旧文件执行软删除标记，使其进入现有清理流程。

### 3. 外链与异常容错

以下情况不应阻塞配置保存：

1. `systemLogo` 或 `browserIcon` 是 `http/https` 外链。
2. 配置字段为空。
3. 路径存在，但 `sys_file` 表里找不到对应记录。
4. `systemLogo` 与 `browserIcon` 使用同一路径。

处理原则：

1. 配置保存是主流程。
2. 附件关联是增强逻辑。
3. 找不到记录时跳过，不让接口失败。

### 4. 旧文件处理策略

旧文件的处理规则如下：

1. 旧路径仍被新配置继续使用：不处理。
2. 旧路径已被替换，且存在 `sys_file` 记录：标记为 `Deleted`。
3. 旧路径不存在记录或为外链：跳过。

这样可以复用现有的删除后延时清理机制，不需要额外新增物理删除逻辑。

## 业务类型设计

为系统配置附件引入稳定的业务类型值：`system_config`。

要求：

1. 该值仅用于标识系统配置关联附件。
2. 应与现有附件业务类型定义保持同一处维护，避免散落字符串字面量。

## 错误处理

1. 系统配置保存失败：直接返回失败，不做附件状态变更。
2. 配置保存成功但附件同步遇到单条异常：记录错误并继续处理其他文件。
3. 如果附件同步整体异常：至少保证配置本身已保存成功，避免因非核心附件状态问题阻塞配置更新。

## 测试设计

### 单元测试

补充系统配置服务测试，覆盖以下场景：

1. 保存包含新 `systemLogo`、`browserIcon` 的配置后，对应文件被标记为 `Associated`。
2. Logo 与 favicon 使用同一路径时，只处理一次，不重复报错。
3. 替换旧 logo 后，旧文件被标记为 `Deleted`。
4. 外链图片路径不会触发附件关联。
5. 找不到 `sys_file` 记录时，配置保存仍成功。

### 集成验证

1. 上传 logo 并保存配置后，检查 `sys_file.status` 是否变为 `Associated`。
2. 手动执行附件清理后，当前配置使用中的 logo/favicon 不应被删除。
3. 替换 logo 后，旧文件应进入待清理路径，新文件仍可访问。

## 验证计划

后续实现完成后，按以下顺序验证：

1. 在 `nest-admin` 中运行 `npm run lint`。
2. 运行系统配置服务相关的最小测试范围。
3. 如涉及前端类型或接口联动，再运行 `nest-admin-frontend` 中最小必要验证。

## 风险与控制

1. 风险：系统配置仍然走基础保存链路，新增逻辑未生效。
   - 控制：显式覆盖系统配置保存接口，并验证前端调用的确进入新逻辑。

2. 风险：旧文件软删除时误删当前仍被其他地方复用的文件。
   - 控制：本次仅处理系统配置自身前后值差异中的旧路径，不做跨业务推断。

3. 风险：业务类型值散落多处，后续难维护。
   - 控制：将 `system_config` 纳入统一业务类型定义。

## 预期结果

修复完成后，系统 Logo 和标签页图标在保存后会被正确标记为已关联，不再在每日孤儿文件清理中被误删；当用户更换图片时，旧文件会按现有清理机制逐步回收。
