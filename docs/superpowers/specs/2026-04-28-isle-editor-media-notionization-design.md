# Isle Editor 媒体块 Notion 化分阶段设计

## 目标

把 `nest-admin-frontend/src/features/isle-editor/components/media-block/media-block.js` 中的图片、视频、附件三类媒体块继续向 `Notion` 靠拢，但采用分阶段方式实施。

本次设计的目标不是一次性把所有媒体能力做满，而是将“交互控制层”和“图片内容能力层”拆开：

- 阶段 1：来源选择与操作层对齐
- 阶段 2：caption / alt / add link / full screen 等图片内容能力对齐

## 范围

本次设计覆盖：

- 媒体块插入后的来源选择方式
- 完成态块的操作入口与 `•••` 菜单模型
- 错误态与重试态的统一控制层
- 第二阶段图片内容能力：caption、alt、link、full screen

本次不覆盖：

- 知识中心业务页改造
- 上传接口与后端协议改造
- 右键菜单、拖拽句柄系统
- 多文件批量上传
- 业务模板与 AI 逻辑

## 已确认约束

用户已明确确认：

- 目标是“都对齐 Notion”，但实现按阶段推进
- 阶段 1 先做来源选择 + 操作层
- 阶段 2 再做图片内容能力

## 当前现状

当前媒体块已经完成多轮演进：

- 支持空块、本地上传、链接插入
- 支持完成态与错误态
- 已有底部悬浮浮层
- 图片/附件有复制链接，完成态可替换、打开、删除

但和 Notion 仍有明显差距：

- 插入来源选择还不够像真正菜单层
- 完成态控制层仍偏显式按钮组，不像 `•••` 菜单模型
- 图片块缺少 caption / alt / add link / full screen 这些关键内容能力

## 为什么要分阶段

“像 Notion”其实包含两类不同问题：

### 1. 交互控制层问题

- 插入时怎么选来源
- 完成态怎么暴露动作
- 错误态怎么恢复
- `•••` 菜单如何组织

### 2. 内容能力层问题

- 图片 caption
- 图片 alt text
- 图片 link
- 图片 full screen / original

如果一轮把两类问题一起做完，改动面会过大，测试和验收都会变得不稳定。

## 方案对比

### 方案 A：全部一次性对齐

做法：

- 一轮同时做来源选择、完成态控制层、错误态控制层、caption、alt、link、full screen

优点：

- 一次性结果完整

缺点：

- 改动面太大
- 难以稳定分层验证
- 出问题时不容易回滚或定位

结论：

- 不采用

### 方案 B：交互层先行，内容能力后补

做法：

- 阶段 1：先让媒体块操作感像 Notion
- 阶段 2：再补图片块能力

优点：

- 最符合当前痛点
- 风险可控
- 每阶段都有清晰产出

缺点：

- 短期内“能力像 Notion”的程度还不是 100%

结论：

- 采用

## 选定方案

选择方案 B：交互层先行，内容能力后补。

原因：

- 用户当前最明显的主观感受是“交互逻辑不像 Notion”
- 先把交互控制层做对，后续再补能力层更自然

## 阶段 1：来源选择与操作层对齐

### 目标

让媒体块从“显式按钮控件”进一步演进为更像 Notion 的控制层：

- 来源选择更像菜单
- 完成态操作更像 `•••` 模式
- 错误态与完成态都走统一控制层

### 阶段 1 核心能力

#### 1. 插入来源选择层

媒体块在空态被选中后，不直接展示一排按钮，而是出现更像菜单的来源选择层。

建议来源选项：

- 上传本地
- 通过链接

图片可额外预留后续扩展位，但第一阶段先不做 `Unsplash` 或图库源。

#### 2. 完成态操作入口分层

完成态块不常驻完整动作组。

建议改成两层：

- 主入口：最常用动作
- `•••` 菜单：完整动作集

目标：

- 控制层更克制
- 更接近 Notion 的 hover/selected 操作节奏

#### 3. 错误态统一进入控制层

错误态不单独像报错控件散开动作，而是：

- 块本体展示错误状态
- 控制层提供：重试上传 / 删除

#### 4. 控制层统一模型

图片 / 视频 / 附件在交互模型上统一：

- 空态：来源选择
- 完成态：操作菜单
- 错误态：恢复菜单

内容呈现允许差异化，但控制层逻辑尽量一致。

### 阶段 1 不做

- caption
- alt text
- add link
- full screen
- 多文件上传
- 右键菜单

## 阶段 2：图片内容能力对齐

### 目标

在阶段 1 交互控制层稳定后，让图片块更接近 Notion 的内容能力。

### 阶段 2 核心能力

#### 1. Caption

图片块支持说明文字。

要求：

- caption 属于图片内容层，不属于浮层动作菜单
- 支持普通文本编辑

#### 2. Alt text

图片块支持替代文本。

要求：

- 通过控制层入口进入编辑
- 不需要一开始暴露在正文中

#### 3. Add link

图片支持绑定链接。

要求：

- 和当前单独的 `复制链接` 区分
- 它是“点击图片跳转到目标”的内容能力

#### 4. Full screen / Original

图片支持：

- 查看原图
- 全屏预览

要求：

- 不要求一开始做复杂图片浏览器
- 先做到用户能沉浸查看图片内容

### 阶段 2 不做

- 图片裁剪 / 蒙版
- 对齐控制
- 复杂图库
- 高级批注与评论

## 两阶段的共同原则

### 1. 编辑器内核优先

所有能力都应落在编辑器层，不依赖业务页。

### 2. 控制层和内容层分离

- 控制层：来源选择、操作菜单、错误恢复
- 内容层：caption、alt、link、full screen

### 3. 图片优先，视频和附件跟进

图片是最能体现“像 Notion 内容块”的媒体类型。

视频和附件优先共享控制层模型，内容能力不必同时做到和图片一样深。

## 验收标准

### 阶段 1 验收

满足以下条件视为阶段 1 达成：

1. 媒体空块来源选择方式比当前更像菜单层
2. 完成态不再像显式按钮条
3. 完成态操作更接近 `•••` 菜单模型
4. 错误态和完成态都通过统一控制层处理

### 阶段 2 验收

满足以下条件视为阶段 2 达成：

1. 图片支持 caption
2. 图片支持 alt text
3. 图片支持 add link
4. 图片支持 full screen / original

## 风险与取舍

### 风险 1：阶段 1 做太多，重新变成一次性大改

取舍：

- 阶段 1 严格只做控制层，不碰内容能力

### 风险 2：阶段 1 和阶段 2 数据结构互相打架

取舍：

- 从第一阶段起就把控制层与内容层职责分开

### 风险 3：图片、视频、附件需求深度不一致

取舍：

- 控制层统一
- 内容能力允许图片先走得更深
