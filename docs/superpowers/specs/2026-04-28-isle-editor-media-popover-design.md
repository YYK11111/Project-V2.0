# Isle Editor 媒体块下方悬浮浮层交互设计

## 目标

优化 `nest-admin-frontend/src/features/isle-editor/components/media-block/media-block.js` 中图片、视频、附件三类媒体块的交互模型，让它们更接近 `Notion`：

- 先插入媒体空块
- 选中空块后，在块下方弹出贴块悬浮小面板
- 由面板承载“上传本地 / 通过链接 / 删除”等动作

本次目标不是重做知识中心业务页，也不是修改上传协议，而是把媒体块从“块内按钮卡片”升级成“块本体 + 下方悬浮浮层”的交互模式。

## 范围

本次设计覆盖：

- 图片、视频、附件空块的选中态交互
- 块下方悬浮小面板的出现逻辑
- 浮层脱离块内部正常文档流后的定位方式
- “上传本地 / 通过链接 / 删除”在面板中的组织方式
- 链接输入态在同一浮层中的切换方式
- 完成态块的操作面板统一模型

本次不覆盖：

- 知识中心业务表单改造
- 上传接口与后端协议改造
- 右键菜单、块级拖拽句柄系统
- caption/说明文字编辑
- 多文件批量上传
- 业务模板与 AI 逻辑

## 已确认约束

用户已明确确认：

- 目标是对齐 `Notion` 的块操作感
- 不要在空块里直接铺开“上传本地 / 通过链接”按钮
- 希望在块被选中后，出现贴着块的悬浮小面板
- 面板里选择“上传本地 / 通过链接”
- 浮层位置优先放在块下方

## 当前现状

当前媒体块已经具备：

- 插入空图片/视频/附件块
- 本地上传与链接插入能力
- 上传中、完成态、错误态
- 替换、打开、复制链接、删除等动作

但当前交互仍偏“卡片控件”而不是“块交互对象”：

- 空块直接在块内展示多个按钮
- 操作区和内容区耦合较重
- 交互入口不够像 Notion 的贴块操作模型
- 当前所谓的 `popover` 仍然是块内部普通 DOM，而不是脱离块布局流的真实悬浮层

## 方案对比

### 方案 A：空块内按钮继续增强

做法：

- 保留块内 `上传本地 / 通过链接 / 删除`
- 只优化视觉和显隐方式

优点：

- 改动最小
- 复用当前结构最直接

缺点：

- 仍然不是 Notion 的块选中浮层模型
- 空块看起来更像表单卡片，而不是待填充块

结论：

- 不采用

### 方案 B：块选中后块下方悬浮浮层

做法：

- 空块本体保持简洁
- 选中块后，在块下方弹出小浮层
- 浮层内提供 `上传本地 / 通过链接 / 删除`
- 链接输入态在同一浮层内切换

优点：

- 最接近 Notion 的操作感
- 内容展示层和动作层分离清楚
- 图片 / 视频 / 附件三类可以统一交互模型

缺点：

- 需要处理选中态、显隐与点击外部关闭等细节

结论：

- 采用

### 方案 C：块级锚点 + portal 浮层

做法：

- 块本体只提供锚点
- 真正浮层挂到编辑器更外层或 `body`
- 通过块位置把浮层定位到块下方

优点：

- 最接近真正的 Notion 浮层
- 不会被块内部布局影响
- 后续碰撞处理更容易

缺点：

- 改动面更大
- 需要处理滚动同步与定位更新

结论：

- 本轮不采用，作为后续升级方向保留

## 选定方案

选择方案 B：块选中后块下方悬浮浮层。

原因：

- 完全符合用户确认的交互模式
- 能把媒体块真正做成“块交互对象”
- 不需要改业务页和上传协议
- 可以先用相对块定位的最小方案落地，再视需要升级到 portal 浮层

## 交互设计

### 1. 空块本体

空图片 / 视频 / 附件块本体只保留：

- 清晰的块边界
- 类型图标或占位符
- 简洁提示文案

不再在块内直接常驻：

- 上传本地
- 通过链接
- 删除

目标：

- 让空块更像一个“待填充块”
- 把操作层完全移到外侧浮层

### 2. 浮层触发条件

当媒体空块被选中时：

- 在块下方弹出贴块悬浮小面板

触发场景包括：

- 鼠标点击块本体
- 块级选中态建立
- 键盘移动到该块（如果当前选中模型已支持）

### 3. 浮层位置

浮层位置固定为块下方，优先保证：

- 用户视线不离开当前块
- 不遮住块本体主要内容
- 不把块本体本身继续撑高

本次第一阶段不要求做复杂碰撞系统，但要满足：

- 浮层脱离块内部正常文档流
- 不再像块底部 footer 一样参与高度计算
- 相对块底部有稳定的间距

实现上允许先使用：

- 媒体块外层 `position: relative`
- 浮层 `position: absolute`
- 浮层定位在 `top: calc(100% + 8px)` 一类的块下方位置

后续如果遇到裁切和碰撞，再升级为 portal 方案。

### 4. 浮层第一层动作

空块选中后的第一层浮层动作：

- 上传本地
- 通过链接
- 删除

动作层级：

- `上传本地` 为主动作
- `通过链接` 为次动作
- `删除` 为危险动作

### 5. 链接输入态

点击 `通过链接` 后：

- 不弹出大对话框
- 在同一块下方悬浮浮层内切换到 URL 输入态

URL 输入态包含：

- 输入框
- 确认
- 返回或关闭

这样可以保持用户焦点仍然停留在当前块附近，而且不会把链接输入区展开到块内容内部。

### 6. 上传中与错误态

块本体负责展示状态：

- 上传中
- 错误

浮层负责提供动作：

- 重试上传
- 重新选择本地文件
- 删除

目标：

- 错误态依然像块状态，而不是独立报错控件

### 7. 完成态块的统一操作模型

上传成功后，完成态不再默认常驻操作区。

建议：

- 完成态块默认只展示内容
- hover 或选中时，再出现块下方悬浮操作面板

图片 / 视频 / 附件完成态动作可统一为：

- 替换
- 打开
- 删除

附加动作：

- 图片 / 附件保留 `复制链接`
- 视频当前版本可以不加 `复制链接`

## 状态模型

建议收敛为两层状态：

### 块内容状态

- `idle-empty`
- `uploading`
- `done`
- `error`

### 交互浮层状态

- `closed`
- `action-menu`
- `link-input`

目标：

- 块内容状态负责内容本身
- 浮层状态负责操作 UI

避免把“内容有没有上传”和“面板是不是打开”混成一个状态机。

## 图片 / 视频 / 附件统一原则

### 统一点

- 空块选中触发浮层
- 浮层主入口一致
- 错误态和完成态操作层一致

### 差异点

- 图片完成态更偏内容块
- 视频完成态更偏预览块
- 附件完成态更偏文件卡片块

即：

- 交互模型统一
- 内容呈现允许差异化

## 职责边界

### `media-block.js` 负责

- 块本体状态展示
- 块下方悬浮浮层显示与切换
- 本地上传与链接输入触发
- 完成态动作面板

### `useIsleUpload.ts` 不负责

- 浮层交互逻辑
- 块选中态逻辑

### 业务页面不负责

- 手写媒体块交互
- 补贴块浮层行为

## 测试建议

至少补以下测试：

1. 空块默认不常驻 `上传本地 / 通过链接`
2. 块被选中时，块下方悬浮浮层出现
3. 浮层不参与块本体高度计算
4. 点击 `通过链接` 后，浮层切换为 URL 输入态
5. 完成态图片块 hover/选中时出现统一操作面板
6. 错误态块仍能通过浮层触发重试或删除

## 验收标准

满足以下条件视为达成目标：

1. 图片 / 视频 / 附件空块不再像表单卡片，而像待填充块
2. 选中空块后，块下方悬浮小面板出现
3. 浮层不再像块内 footer 一样把块本体撑高
4. 用户可在浮层中选择“上传本地 / 通过链接”
5. 链接输入态在同一浮层内切换，而不是弹大对话框
6. 完成态块的操作模型比当前更接近 Notion

## 第一阶段不做事项

以下能力明确不纳入这一轮：

- 右键菜单
- 块级拖拽句柄系统
- caption 编辑
- 多文件批量上传
- 业务模板与 AI 逻辑
- 工具栏级联动浮层

## 风险与取舍

### 风险 1：浮层与块选中态联动复杂

取舍：

- 第一阶段只做媒体块自己的最小浮层状态管理
- 不引入全局块句柄系统

### 风险 2：块下方绝对定位浮层可能被裁切

取舍：

- 第一阶段先接受相对块绝对定位方案
- 如遇到滚动容器裁切或边界碰撞，再升级为 portal 浮层

### 风险 3：完成态和空态交互过于分裂

取舍：

- 统一使用“贴块浮层”作为操作层
- 只让块本体负责内容与状态显示

### 风险 4：不同媒体类型需求不完全一致

取舍：

- 先统一交互模型
- 保留内容表现差异化
